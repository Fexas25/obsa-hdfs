# obsa-rust

华为云 OBS/PFS 的 Rust 核心、JNI 桥接和可选 Hadoop 适配层。

## 当前状态

已从缺失文件、无法构建的骨架推进到可运行的本地实现：

- 核心文件操作：stat、exists、open/create、mkdirs、list、delete、rename、truncate、append、content summary、权限元数据。
- 正负缓存、LIST 回填、PFS 双键删除与按深度分组删除、可配置 trash。
- 已有缓存条目原位更新，避免满缓存时扫描淘汰；命中使用共享读锁，新键准入串行化以保证容量上限。
- LIST 检测多页标记循环；同页目录前缀使用集合去重，保留已有目录元数据；文件默认权限与 HEAD 一致。
- LIST 同页对象键重复时返回错误，即使重复项元数据一致；避免含糊结果进入后续复制/删除。复用页内集合，不新增跨页索引；目录前缀与目录对象的正常合并保持不变。
- LIST 返回对象及目录前缀必须属于请求范围；异常响应在目录复制/批量删除前被拒绝。PFS 递归删除移动键名并缓存排序深度，减少复制及重复扫描。
- rename 的 overwrite 仅允许文件替换文件；目标为目录时先解析实际子路径，拒绝文件/目录类型冲突及已有目录合并。
- rustls HTTPS、连接并发限制、每次重试重签名；MPU 初始化/完成及 PFS rename 禁止自动重试，避免重复发起结果不确定的操作。
- 5xx 自动重试限定为 500/502/503/504；501 批量删除直接进入逐项删除回退，减少无效请求和退避等待。
- 可重试操作支持 429 限流；读取 `Retry-After` 秒数或标准 IMF-fixdate 日期，等待服务端要求与本地退避的较大值。无效字段回退本地策略，过去日期不缩短本地退避；长等待可由请求总期限中断。等待前释放响应缓冲，非幂等操作和已耗尽重试的请求直接返回原响应。绝对日期依赖本机时钟，旧式 HTTP 日期格式尚未验证。
- 签名请求和底层 HTTP 共用重试次数、错误分类与线性退避策略。`fs.obs.retry.max.attempts` 表示首次请求以外的重试次数（默认 2，0 禁止）；`fs.obs.retry.backoff.ms` 为退避基数（默认 100 ms，第 n 次重试等待 n 倍，0 不等待）。两者接受非负十进制整数并支持桶级覆盖；非法/溢出值回退默认值。显式配置超过 2 次现会生效，应计入调用耗时与请求量。
- `fs.obs.connection.timeout` 为单次 HTTP 尝试的总期限（毫秒，默认 60000），覆盖连接额度排队、发送/响应头和完整响应体；各阶段不重新计时。相比旧行为，排队过久或各阶段累计超时会更早失败。重试和退避仍另计，不是整个文件操作的总期限。
- `fs.obs.request.timeout.ms` 为一次 HTTP 请求跨全部重试与退避的总期限（非负整数毫秒，默认 0 关闭，支持桶级覆盖）。总期限耗尽返回 `HTTP request total timeout`，不会再进入同一重试循环；连接额度和响应等待随本地取消释放。该设置不覆盖整个目录操作，也不能撤销已发送的远端写入。
- 批量删除要求完整 DeleteResult XML 且不存在 Error 项，拒绝空响应、截断结果及缺少 Code 的失败项。
- 有界预读、完整分块读取、分片上传等待与失败清理、小文件单 PUT。
- MPU close 按完成顺序处理分片，失败后取消并回收剩余请求，避免被卡住的分片拖住失败处理；等待过程保留任务所有权。
- close 等待 abort 时保留上传 ID；取消或 abort 失败后，Drop 在运行时可用时再尝试一次清理。Drop 先取消并回收本地分片任务，再发出清理请求。
- 分片 ETag 作为不透明文本进行 XML 转义，避免特殊字符破坏完成请求。
- 块内 seek 复用读取缓存；后台上传错误在后续 write/flush 提前暴露，已完成任务及时回收。
- seek 命中预读范围时保留目标块的就绪数据或在途任务，避免取消后重复 GET；其余预读取消。目标任务沿用原有版本检测，EOF 及范围外 seek 取消无关任务。
- 单次大 read 逐块补充预读，避免整个调用退化成串行 GET；取消预读等待后可复用原请求。
- 顺序访问检测按连续读完的块计数，三个块完成后启动预读；块内多次小 read 不再误触发后续大块下载。seek 重置进度，预读仍在大 read 内逐块补充。
- 读取复制长度先受实际缓冲容量限制再转换，避免 32 位 usize 截断大文件剩余长度产生零进度；块内偏移使用可检查转换。小数据模拟覆盖 4 GiB 及接近 u64 上界的读、seek 和 EOF，本机尚未执行 32 位目标验收。
- GET 单帧响应复用原缓冲区；多帧响应按请求范围大小一次分配合并空间，减少增长复制。仍验证响应结束、长度及迟到错误。
- 删除/重命名部分失败或取消时清理涉及路径的缓存，避免继续返回已删除文件或旧的不存在结果。
- 上传 write 中途取消后拒绝继续写入或提交，避免缺失分片却报告成功；需丢弃该流并重新创建。
- PFS append 保留取消等待的任务句柄；flush 可重新等待，丢弃流会取消任务。每次追加任务结束都会清理状态缓存。
- PFS append 按块复制，所有通过同一文件系统打开的追加流共享字节额度；复制前先申请额度，任务结束/失败/取消后释放。部分 write 被取消后流持续报错，避免误报完整成功。
- 多分块 read 在失败或取消后恢复逻辑位置、顺序块计数和预读窗口，JNI/Java 重试不会静默跳过已经读取但未交付的数据，也不会重复累计失败调用中的顺序进度；仍保留可复用的预读任务。
- 普通桶读取固定 ETag，后续 GET 带 If-Match，校验响应并拒绝跨版本混读；复用 HEAD/LIST 状态，不增加额外 HEAD。
- Hadoop CredentialProvider 获取通用及桶级 AK/SK/token，遵守明文回退开关；Rust Debug 隐去敏感配置。
- JNI 文件系统/流句柄、异常边界、读写/seek/flush/close；读取直接填充调用方数组，写入只复制指定区间，原生暂存每批最多 1 MiB。
- HTTP 响应体限额、错误体限额，以及 Range 的 206/Content-Range/长度验证；拒绝服务端忽略范围或错位返回。
- CopyObject 源路径按段 URL 编码；复制和 MPU 完成校验完整成功 XML/ETag，阻止 HTTP 200 内嵌错误触发后续删源。
- LIST/MPU 初始化拒绝截断、错误根节点、多文档和错误实体；LIST 大小、分页布尔值不再静默回退。
- 普通桶删除/迁移最后一个子项前保留父目录 marker；PFS create 在返回流前校验目录冲突。
- Hadoop 创建 builder 的非递归重载、append/truncate 能力查询、append 流同步能力和关闭流校验。
- 独立的 `OBSFileSystemRust`，使用 `fs.obs.impl` 显式启用；原 Java 参考工程未修改。

**尚未达到原交接文档的生产验收标准。** 参考 S3A / Aliyun OSS 后的实施顺序及验收条件见 [适配器实施计划](docs/ADAPTER_PLAN.md)。 以下验证全部使用本地内存存储或 loopback HTTP 服务，不需要云账号。

## 分页与目录容量统计

Rust 提供 `listing::ListPager::new(store, prefix, delimiter, page_size)` 和 `next_page().await`。每次调用最多获取一页；`Some(vec![])` 是空页，`None` 才是结束。构造及停止消费不会请求后续页面。取消等待不推进游标；传输错误可重试当前页，协议校验错误保持失败，防止跳过损坏页。

`get_content_summary` 已逐页统计，不再保留全部文件条目，并检查累计大小溢出。内存包含当前页、分页标记历史、不同目录名和用于拒绝跨页重复的已见对象键；随对象数与键长度增长，不是全流程恒定内存。`list_all` 基于同一分页器收集全部页面，删除/重命名继续在列表校验后处理子对象；Hadoop `listStatusIterator` 创建时取首个可用页面，随后按需获取。Rust `StatusCursor` 管理跨页去重、marker 历史及终止错误；Java 仅包装一页 FileStatus 和迭代接口。JNI 游标在 EOF、错误或所属文件系统关闭时释放，迭代器也实现 `java.io.Closeable`，可在提前结束时显式释放；被遗弃的迭代器使用 PhantomReference 队列兜底，回收时间取决于 JVM，不能保证立即释放。没有后台取页任务，Rust 状态仍随条目/页数增长，并非恒定内存。`listStatus` 和旧 Rust `list_files_recursive` Vec API 仍全量返回；Hadoop `listFiles` 已使用下述分页路径。

## Hadoop 启用方式

将适配层 JAR 与其 Jackson 依赖加入应用 classpath，native 库目录加入 `java.library.path`。

```xml
<property><name>fs.obs.impl</name><value>org.apache.hadoop.fs.obs.OBSFileSystemRust</value></property>
<property><name>fs.obs.endpoint</name><value>YOUR_OBS_ENDPOINT</value></property>
<property><name>fs.obs.bucket.mode</name><value>auto</value></property>
```

AK/SK/token 可由 Hadoop CredentialProvider 提供，通过 `hadoop.security.credential.provider.path` 配置。
别名为 `fs.obs.access.key`、`fs.obs.secret.key`、`fs.obs.session.token`，也支持对应的 `fs.obs.bucket.BUCKET.*` 别名。
遵守 `hadoop.security.credential.clear-text-fallback`；启用时可回退到本地 Hadoop 配置。
当前只在初始化时读取凭据，尚未支持自动 STS 刷新和委托令牌。隔离 user:// 提供器已测试，JCEKS/第三方提供器部署仍需验证。

普通桶默认 `fs.obs.read.change.detection.enabled=true`：HEAD/LIST 或首次 GET 固定 ETag；
版本变化或响应缺少 ETag 将抛 IOException，失败后需关闭并重新打开流。
设为 false 可兼容不返回 ETag 的后端，但失去此项混读保护。PFS 本轮仍采用可变文件读取语义，不承诺快照一致性。

默认 `fs.obs.http.response.max.bytes=67108864`（64 MiB）限制单个缓冲响应体；
Range GET 还受实际请求范围长度限制，错误响应最多 64 KiB。HEAD 的 Content-Length 是对象长度，不套用响应体限额。
预读块大小应不大于该限额；直接读取超过限额的整对象会失败，应改用范围读取或显式调整限额。
这不是进程 RSS 的全局上限：并发响应、缓冲合并、上传和各流持有的数据仍需统一字节预算。

PFS 追加配置：

- `fs.obs.pfs.append.concurrency`：默认 4，每个追加流的最大并发请求数；与共享字节预算共同约束实际并发。
- `fs.obs.pfs.append.chunk.size`：默认 1 MiB，每次复制并提交的数据块上限。
- `fs.obs.pfs.append.total.bytes`：默认 64 MiB，同一文件系统所有追加流的请求体额度；支持 `k/m/g` 后缀和桶级覆盖。
- 实际块大小不大于字节额度，避免单块永远无法取得额度；额度最小 1 字节，最大受 u32 与平台 Semaphore 上限限制。
- 额度不包含调用方数组、HTTP/TLS 内部缓冲、远端存储及其他读写路径，不能当作进程 RSS 上限。直接调用 Rust `PfsAppendStream::new` 创建的是独立额度；通过 `ObsFileSystem::append_stream` 才共享文件系统额度。

部分追加 write 失败或取消后，应丢弃流并核对远端状态；已到达服务端的数据无法本地回滚。单纯取消 flush 仍可继续等待原有任务。

## 顺序读取本地对照测量（2026-09-26）

Windows、debug 构建、单线程 Tokio、本地内存存储；4 MiB 文件、64 KiB 范围，
每次 GET 注入 5 ms 延迟（实际受 Windows 定时器粒度影响），预读窗口和全局额度均为 8。
单次 read 读取整个文件，每组 3 次，逐字节校验内容。此延迟微基准关闭 ETag 检测与模拟端散列计算，以保持原对照条件；不代表默认完整配置。
优化前耗时 976.151 / 976.306 / 985.142 ms；优化后 188.109 / 182.464 / 175.247 ms。
中位耗时缩短约 5.35 倍，GET 数均为 64，并发峰值由 1 变为 8。
这是延迟受限模拟场景的对照结果，不代表真实 OBS 吞吐、CPU 性能或生产环境收益。
复现命令：`cargo test -p obs-rust-core --test filesystem benchmark_large_sequential_read -- --ignored --nocapture`。

Windows、debug 构建、单线程、1024 个负缓存条目、TTL 60 秒；预填充后按顺序循环更新已有键 2000 次，每组 3 次。

## 与旧交接文档不同的实现决定


- 普通 LIST 参数 `prefix/delimiter/marker/max-keys` 不进入 OBS V2 canonical resource；
  操作子资源按字典序排序。依据华为官方 Header 签名文档：
  https://support.huaweicloud.com/api-obs/obs_04_0010.html
- PFS DELETE 必须保留 404，否则双键删除无法从目录探测继续到文件。
- 两种模式的 overwrite create 都需在缓存未命中时确认目标不是目录，避免返回流后才发现类型冲突。
- 普通桶保留隐式父目录会额外检查 marker，缺失时写入；已有 marker 不主动覆盖。并发外部修改仍不具备原子保护。
- CopyObject 的中文及 `%` 编码遵循 [华为复制对象 API](https://support.huaweicloud.com/intl/zh-cn/api-obs/obs_04_0082.html)，同时编码保留字符以消除路径歧义。
- If-Match 将修订值作为带引号的强 ETag 发送，依据 [RFC 9110 §13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match)。
- LIST 只有 inode number 时不能虚构 dentry name；仅完整的服务器双字段提示会用于 GET。
- 分页缺少有效推进标记时返回错误，避免无限循环。

原始 35 项 API 与配置接线现状见 [覆盖核对](docs/API_COVERAGE.md)。Rust 已实现但 JNI 未接通、仅继承 Hadoop 默认行为及解析但未使用的配置，均单独列为缺口。

`fs.obs.block.size` 设置 Hadoop 逻辑块大小，默认 128 MiB，支持正整数字节数或 k/m/g 后缀及桶级覆盖。零值、负数、溢出和非法文本回退默认值（非法桶级值覆盖通用值后回退默认）。Rust 统一解析，Java 默认值和状态使用同一结果。它不控制 OBS 分片上传大小，也不将对象拆成 HDFS 物理块。

`fs.obs.content.summary.enable` 现在实际控制 Hadoop 容量统计路径：默认 false 使用 Hadoop 默认目录遍历；true 使用 Rust 平铺 LIST 逐页汇总。支持 `fs.obs.bucket.<bucket>.content.summary.enable` 覆盖，配置在初始化时固定。此前版本忽略此开关、始终调用 Rust；要保留该路径请显式开启。直接 Rust `get_content_summary` API 仍执行平铺统计，开关控制的是 Hadoop 兼容层策略。两条路径都不是目录变更期间的一致性快照。

PFS 数值权限/所有者元数据更新会先 HEAD 读取最新自定义元数据，仅替换指定字段后提交 REPLACE，避免删除无关 x-obs-meta-*。权限变更保留文件类型位，失败/取消使缓存失效。这条路径不再承诺零 HEAD；并发 HEAD/PUT 之间仍可能发生写入竞争。Hadoop 名称型 setOwner 已通过独立 disguise 路径接通，不能与数值 uid/gid API 混用。

## Hadoop 名称与展示权限

设置 `fs.obs.permissions.mode=disguise` 后，PFS 的 Hadoop `setOwner` 写 `user/group` 自定义元数据，`setPermission` 写十进制 `permission`；HEAD 与列表读取这些展示字段。默认 `none` 或普通桶下两种操作不写元数据。支持桶级覆盖，未知模式在初始化时报错。

一个 owner/group 为 null 时保留旧值，两个均 null 报错；disguise 模式暂限非空可打印 ASCII，Unicode/控制字符明确拒绝。更新保留其他自定义元数据并失效缓存，但 HEAD+PUT 仍不是原子操作。LIST 不含这些自定义字段，所以 disguise 模式会额外逐条 HEAD；none 模式保持原列表请求路径。此功能不是服务端 ACL 或用户鉴权。

兼容变化：此前 Hadoop setPermission 直接改数值 mode；现在遵守原 Java 的模式开关，默认不写入，启用后改展示 permission 字段。直接 Rust set_permission/set_owner 的数值 API 保留。新版 Java/JNI 与 native 库需配套部署。

## 缓存淘汰优化（2026-10-10）

StatusCache 改用惰性最小堆索引，避免满缓存每次新键准入都扫描全部条目。读取和已有键更新仍走 DashMap 分片与原子访问序号，不获取索引锁；新键准入串行，保留顺序执行下的 LRU 行为。淘汰重新核对访问序号，采用快照截点防止持续并发访问无限推迟准入。同名重建用代次区分，索引最多保留容量两倍的记录，达到上限时重建。大量访问后的首次淘汰仍可能刷新多个堆项；索引重建会扫描缓存，不承诺每次写入恒定耗时。

[优化后同条件原始样本](docs/benchmarks/listing-cache-20261010.json)：1 万条目、4096 项缓存的完整耗时中位数，全量 1451.58 → 200.10 ms（减少 86.2%），分页 1527.21 → 152.85 ms（减少 90.0%）。每组仍为 10 次 LIST，分页首批一次请求。关闭缓存的完整耗时变化约 -0.1% 至 +2.4%，未见同量级变化。本地 release 合成基准，未测真实云吞吐、RSS 或高并发尾延迟；新增索引的实际内存成本仍需测量。

2026-10-10 补充：全量失效（空前缀或 `/`）现在与新键准入使用同一锁，清空条目后立即丢弃淘汰堆，释放其路径字符串及分配容量；不必等下一次写入整理。局部失效仍采用有界惰性清理。8 线程混合读取、更新、淘汰和清空的回归检查存活条目的索引唯一性及后续淘汰，并额外重复运行 20 次；这不是无竞争的证明，也不是高并发尾延迟或进程 RSS 测量。本轮未重跑上面的 release 吞吐基准，其数字仍对应上一轮源码。

## 缓存集中刷新优化

2026-10-10：旧访问序号需要刷新时，改用 `BinaryHeap::peek_mut` 原地更新堆顶，退出 guard 时修复堆序，避免同一索引的出堆再入堆。失效记录仍移除；LRU 代次校验、并发截点和容量规则保留。

`-BenchmarkCache` 现同时运行“全量访问后单次准入”的专项基准：容量 128/4096，每次先依 LRU 顺序读取所有存活条目，再计时一个新键写入，并断言正确淘汰最旧键、条目数保持容量。每组预热一次、五轮正式测量，每轮 50 次准入。[同机修改前后样本](docs/benchmarks/cache-refresh-20261010.json)中，五轮 P50 的中位数分别从 12.5 降到 8.0 微秒（-36%）、449.6 降到 339.8 微秒（-24.4%）。专项 P99 因每轮仅 50 次采样等于该轮最大值，不作为稳定尾延迟结论。

普通单写场景中位数仍为 2.0 微秒；混合读写本轮仍观察到 3.1235 毫秒的单次写入。前后按顺序运行，未控制系统后台调度，未测 CPU/RSS；这证明了当前样本中集中刷新的局部收益，不能解释此前所有异常值或承诺全局尾延迟改善。

## 上传排队期间的失败传播

2026-10-10：普通桶分片上传在等待单流/全局上传名额时，会同时处理本流已提交分片的完成结果。已有分片失败会中断排队并返回原始错误，不必等无关上传释放名额；成功分片保留给最终合并，名额申请 future 持续保留以维持排队位置。仍按单流名额、全局名额的顺序申请，失败状态持续生效。

新增虚拟时间用例复现并修复写入、关闭尾块两种排队超时；检查不提交下一分片、不执行 complete、执行 abort，且归还名额。另验证取消排队后不会丢失运行中分片的所有权，Drop 取消分片后执行清理。已有多分片与短尾块内容校验继续通过。

这解决的是已有任务失败被资源排队遮住的问题；未增加整个文件操作的总期限，也未完成统一读写字节预算。调用方保持失败流时仍应关闭或丢弃流；Drop 的远端清理仍是 best effort，不保证进程退出后的服务端残留回收。本轮未宣称吞吐提升。

## PFS 追加的完成顺序与失败清理

2026-10-10：PFS 追加按任务完成顺序处理结果，避免较早请求卡住时遮住较晚请求的错误；等待并发名额或共享字节额度时也能观察本流任务失败。首次错误持续保留，取消其他待完成任务；flush 会等这些任务退出再返回错误，任务释放对应字节额度。等待字节额度的 future 不因处理完成事件而重建，保持原有排队位置。

四个新增用例覆盖 flush 被早请求阻塞、并发上限等待、其他流持有共享额度，以及后提交请求先成功时取消 flush 后恢复。验证失败后不提交后续块、额度可被新流重新使用，成功乱序完成时最终内容和后续偏移正确。

本地取消不等于远端回滚：PFS 在失败前可能已有部分写入，客户端不承诺追加原子性。调用方主动取消 flush 且未发现任务错误时仍可恢复；已有失败或部分 write 被取消后，流持续失败。统一读写字节预算、整个操作期限和真实服务验收仍未完成。

## 读取合并缓冲区的容量错误

2026-10-10：读取响应合并先检查预期范围是否能表示为平台缓冲区容量（不超过 `isize::MAX`），不合法时返回 InvalidArgument。收到第二个非空数据帧需要合并时，使用 Vec 的可失败预留接口，分配器报告失败时返回 Io 错误，避免这处不可失败分配导致的容量 panic。单帧仍复用原 Bytes；多帧沿用按预期范围一次性预留策略，保留内容顺序、短响应、额外帧与 EOF 后错误校验。

回归用两个单字节帧和极大逻辑范围复现了旧实现的 capacity overflow；没有申请巨量实际内存。未注入真实物理内存不足，也未验证 32 位构建；本改动不等于统一内存预算或避免所有 OOM，其他分配及操作系统资源终止仍不在这处错误处理的保证范围内。

## 并发配置的信号量边界

2026-10-10：正式 Rust `ObsFileSystem::from_config` 和 JNI/Hadoop 初始化在创建连接池、探测桶之前，检查 connection.maximum、upload.active.blocks、upload.total.active.blocks、readahead.total.chunks 四项配置（均带 fs.obs. 前缀）。超过当前平台 Tokio `Semaphore::MAX_PERMITS` 返回 InvalidArgument；JNI 映射为 IllegalArgumentException，错误指出具体配置键。桶级覆盖解析后执行同样检查。

保留已有直接构造接口的签名：HttpPool::new、ObsFileSystem::with_store、ObsInputStream::new、ObsOutputStream::new 将超大名额限制到该表示上限，防止构造信号量 panic。连接/上传零值仍归一为 1，预读全局零值仍禁用预读。该上限只是运行库可表示范围，不是推荐并发值或实际内存预算；不改变正常配置的数据路径，不据此宣称吞吐提高。尚未完成全部配置边界、统一读写字节预算或 32 位运行验收。

## 上传缓冲区配置的容量边界

2026-10-10：`fs.obs.multipart.size` 和 `fs.obs.multipart.threshold` 在正式初始化时进行可检查的平台容量转换，超过 `isize::MAX` 返回带配置键的 InvalidArgument，JNI 映射为 IllegalArgumentException。桶级覆盖解析后同样校验。避免 u64 直接转换为 usize 在窄平台上截断；原有最小分片 5 MiB、最小阈值 1 字节规则保留。

直接 `ObsOutputStream::new` 保留不返回 Result 的签名，遇到非法容量时创建持续失败的流；write（包括空写）、flush、close（包括未写入就关闭）均返回配置错误，不提交存储请求。表示范围内的容量不等于实际可分配内存或服务端允许的分片大小；尚未建立统一上传字节预算、覆盖所有分配失败或完成 32 位运行验收。

## 上传跨阈值时提前启动 multipart

2026-10-10：write 根据已有缓冲长度与本次输入长度判断是否跨过 multipart 阈值；一旦足够，先初始化 multipart，再按分片大小填充缓冲，避免先为本次输入扩展到整个阈值。比较使用饱和减法，不相加产生溢出。已有低于阈值的缓冲会保留并按顺序排出，小文件仍在 close 时单 PUT。

初始化失败时不复制本次输入，错误持续生效；这也提前了该 write 内初始化请求的时间，不改变 close 提交契约。已有缓冲可能大于单个分片，多个 write 累积到阈值之前的缓冲仍可能较大；本项不是全局字节预算，未进行 RSS 或吞吐基准，不能据此量化内存峰值/吞吐收益。

## 失败上传流的本地资源释放

2026-10-10：write 返回错误、flush 观察到分片错误，或后续操作发现此前 write 已取消时，立即丢弃该流的本地缓冲及已完成分片信息，并对其余分片任务发出取消。保留任务句柄和 upload ID，供 close/Drop 等待任务退出后清理远端 MPU；持续返回首次错误，不再提交 complete。

取消请求不代表任务已经同步退出：任务获调度退出后才释放其请求体和并发名额。调用方即使暂时保留失败流，也无需等 close/drop 才开始取消这些任务。未再次调用流的取消 write，或尚未被流观察到的后台错误，仍需后续操作/Drop 才触发处理；远端 MPU 清理仍依赖 close/Drop，不能保证远端回滚、进程退出后的清理或全部分配立即归还操作系统。

## PFS 取消写入后的共享额度回收

2026-10-10：PFS 追加流在后续 write 检测到先前 write 被取消时，也会立即请求取消已有任务；不再仅报错并保留运行中任务直到 flush/close/Drop。所有写入执行错误出口统一取消剩余任务，任务句柄保留给 flush/close 排空，首次错误持续生效。任务退出时释放追加字节额度并执行原有元数据失效回调。

覆盖并发数量等待和共享字节额度等待两条取消路径，验证原流仍存活时另一流可以使用完整额度。任务退出依赖运行时调度；没有后续操作且未 Drop 的取消 write 不会被主动检测。取消不是已提交 PFS 数据的回滚；正常 flush 被取消后仍允许恢复，其原有语义不变。

## 读取错误后的预读资源释放

2026-10-11：read 返回错误时，回退本次读取游标/预读进度，同时丢弃驻留块并取消、移除其他预读任务，避免调用方暂停重试时继续持有预读名额和数据。此清理现覆盖普通传输错误；RemoteFileChanged/MissingVersion 仍持续报错，其他读取错误仍允许在同一流上重试，并保留原有 ETag 约束。

主动取消 read future 不走上述错误返回路径，仍保留可恢复的预读请求；既有取消后恢复与 seek 复用语义不变。清理可能令重试重新获取已预读范围，这是释放失败读取资源的取舍。任务取消及名额归还依赖运行时调度；本轮未量化 RSS/吞吐收益，也未完成统一读写字节预算。

## HTTP 响应帧的逐步合并

2026-10-11：HTTP 层不再收集全部数据帧后一次性转为连续 Bytes。单个非空帧直接复用原分配；出现后续帧时逐步合并，复制后释放原帧。合并缓冲按已接收长度几何增长，使用可失败预留，申请容量受响应限额和平台容量限制；已校验长度的限额预留见下一节；Body size_hint 不用于预分配。

保留 Limited 的累计字节限制、头部长度/Content-Range 检查、同一次尝试的整体响应期限，并读到 EOF 以识别后续错误。空数据帧和 trailers 不进入响应数据。此改动减少收集器持有的帧对象，但扩容可能再次复制已接收内容；未量化 CPU、吞吐或 RSS，不能当作全局内存预算或避免所有 OOM 的保证。

## 状态查询与缓存失效的并发保护（2026-10-11）

get_file_status 在远程查询前记录缓存失效代次，返回后只在代次未变时回填。代次检查与回填由读锁保护，单键、前缀和祖先失效持写锁，防止检查通过后又与失效交错。普通缓存命中不获取此锁。

这修复了删除已完成、先前暂停的 HEAD 才返回并重新缓存旧文件状态的问题。保护覆盖状态查询的普通 HEAD、目录标记 HEAD、隐式目录判断和不存在结果。已经开始的查询仍可能返回旧快照，但失效后的旧查询不能继续污染缓存。

当前采用全缓存代次：无关路径的失效也可能抑制正在进行的查询回填，增加后续缓存未命中；本轮未测量锁开销或吞吐。LIST 回填、创建完成回调和 mkdir 写回尚未纳入此保护，也不能检测其他客户端对云端的修改。

## LIST 回填的失效保护（2026-10-11）

在上一轮状态查询保护基础上，完整目录列表、分页目录/文件列表及递归文件列表在发起 LIST 前记录缓存失效代次；子项和父目录回填使用该代次。PFS disguise 模式下补充元数据的 HEAD 也沿用列表开始时的代次，不能在子项处理时重新取代次而放行旧 LIST 快照。

## 创建和 mkdir 成功回填的并发保护（2026-10-11）

创建流在完成父目录处理后记录缓存代次，mkdir 在操作前记录代次。成功返回时，缓存用同一写锁检查代次、推进代次、清除目标及祖先，然后仅在原代次仍匹配时缓存返回状态。成功完成也会阻止更早的 HEAD/LIST 查询继续回填。失效和条件回填之间没有解锁窗口。

发生并发失效时，不使用迟到响应构造缓存，也不保留目标路径的既有缓存：远端实际提交顺序可能与响应顺序不同，后续查询重新确认当前状态。无竞争时仍直接缓存长度、权限和块大小。全局代次意味着无关路径修改也可能触发保守失效；没有本轮性能测量。

本轮仅处理成功返回的缓存写回；创建或 mkdir 在服务端已提交但客户端报错、取消等情况下的失效清理仍需补齐，不提供跨客户端强一致性或远端事务保证。

## 创建和 mkdir 的不确定提交清理（2026-10-11）

创建流的成功回调现在持有缓存失效守卫；关闭失败、关闭被取消或流被丢弃而未执行回调时，守卫随流释放，清除目标前缀与祖先状态。mkdir 在开始远端修改前持有同类守卫，错误、取消及 PFS 返回 false 的退出路径都会执行清理。成功条件回填后解除守卫，保留上一轮验证的正常缓存命中和权限。

本地模拟在保存对象后暂停响应，再注入传输错误或取消任务，验证缓存不会继续保留旧长度或不存在结果。创建测试包含普通 PUT 与分段上传完成、首次创建与覆盖、OBS/PFS 两种模式，共 16 种组合；mkdir 测试包含两种模式与错误/取消，共 4 种组合，并检查祖先负缓存清理。既有成功回填和并发删除/覆盖回归仍通过。

该清理是客户端退出时的本地缓存失效，不是服务端回滚或提交确认。如果远端直到取消清理之后才真正提交，后续查询仍可能受服务端可见性及缓存 TTL 影响。丢弃尚未发起远端写入的流也会保守失效，可能增加后续查询；本轮没有新增性能测量，未验证真实云服务。

## truncate 的全部退出路径失效（2026-10-11）

PFS truncate 在发出远端请求前持有单键失效守卫。成功、错误或 future 被取消时均清除目标缓存，并通过已有失效代次阻止更早的状态查询重新回填旧长度。原实现仅在成功时失效，已复现服务端截断后返回错误仍读取原长度，以及更早 HEAD 迟到回填的问题。

截断不改变目录成员，因此这里采用借用缓存和键的专用守卫，只失效单键，不构造键列表、不扫描前缀，也不增加 HEAD。错误和取消仍保持原结果；缓存清理不代表远端回滚或确定的提交状态。

## 内部缓存回调与用户回调隔离（2026-10-11）

Rust 调用方对 ObsFileSystem 返回的创建流设置 on_close、对追加流设置 on_flush，原先会替换文件系统安装的缓存清理回调。新回归复现创建完成后仍命中负缓存，以及追加完成后仍命中旧长度。

## 追加回调前归还共享字节配额（2026-10-11）

## 空追加写入的后台错误传播（2026-10-11）
