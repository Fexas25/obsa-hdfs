# 大目录分页的本地测量

此基准比较 Rust `list_files_recursive` 的全量返回与 `StatusCursor` 的逐页消费。
它生成平坦目录，不发送 HTTP，不包含 JNI/Java 序列化，不代表真实 OBS/PFS 性能。
默认模拟每次 LIST 等待 1 ms，但 Windows 实际调度等待可能明显更长；报告墙钟时间时必须保留这项限制。
使用 `-DelayMs 0` 可隔离模拟定时器成本；这仍然不是 HTTP 后端测试。

## 运行方法

先在 Windows 编译并检查默认基准：

```powershell
.\scripts\build-windows.ps1 -BenchmarkListing
```

使用该命令输出的 `filesystem-<hash>.exe` 的实际路径（不要照抄占位符），分别运行：

```powershell
.\scripts\benchmark-listing-memory.ps1 -TestExecutable 'target\release\deps\filesystem-<hash>.exe'
.\scripts\benchmark-listing-memory.ps1 -TestExecutable 'target\release\deps\filesystem-<hash>.exe' -ReverseOrder
```

默认测量 100000/1000000 个文件，每种规模与模式独立进程，预热一次、记录三轮；
`-Entries` 支持 1..1000000，`-Trials` 支持 1..20。过小负载可能无法捕获工作集样本，脚本会报错。
`-DelayMs` 支持 0..1000，`-WarmupMs` 支持 0..10000；预热为至少一轮，
指定持续时间后重复完整预热轮次直到达到该时间，之后才开始正式计时记录。
小目录比较可使用 `-WarmupMs 200` 减少启动阶段影响；进程 CPU/墙钟仍包含全部预热，
因此持续时间预热的进程 CPU 不适合直接当作固定工作量的 CPU 对照。
每次写入新的 target 子目录，可用 `-OutputDirectory` 指定不存在的输出目录。
脚本检查条目数、LIST 请求数、变体和轮次，旧二进制忽略参数时不能静默产生有效结果。

也可直接使用 `OBS_LIST_BENCH_ENTRIES`、`OBS_LIST_BENCH_TRIALS`、`OBS_LIST_BENCH_VARIANT`、
`OBS_LIST_BENCH_DELAY_MS`、`OBS_LIST_BENCH_WARMUP_MS`
运行测试二进制。entries 未设置时保留原有 10000/100000/10000+4096 缓存的三组对照；
设置 entries 时关闭元数据缓存以隔离扫描开销。variant 仅接受 eager/paged，未设置则逐轮交替。
输出同时记录首条/全程 LIST 和 HEAD 数；非整页数量的 LIST 数按向上取整验证。

## 内存指标边界

脚本每 100 ms 读取 Windows 进程 PeakWorkingSet64，并记录观测最大值。
这是包含运行时、分配器保留页和预热的进程工作集峰值，不是 Rust 精确堆分配，也不是 Linux RSS。
不同模式使用独立进程，避免先前模式保留的分配器内存污染后一模式的进程峰值；
反转运行顺序用于检查时间顺序影响。不能把两个进程峰值之差直接称为受控缓冲预算节省。
脚本记录的进程 CPU/墙钟包含预热和全部轮次；每轮指标来自 Rust 内部计时。
全量路径的内部计时截止于整表构造完成，不含最终结果析构；分页路径逐页消费并释放，
这些逐页释放包含在扫描计时中。进程级 CPU/墙钟则包含两种模式的结果析构。

分页仍保留路径去重、marker 历史以及按需祖先检查状态，不能因每页最多 1000 条就声称
整个扫描使用常量内存。完成/失败释放状态的回归另在 listing 模块中。
此平坦目录不能覆盖深层路径冲突、百万不同祖先或 Hadoop 端对象内存；这些需要独立负载。

## 2026-10-17 结果

先后两次执行，第二次反转变体顺序；八个独立进程共 24 条正式轮次记录，预热另计。
所有条目数断言通过；十万条每轮 100 次 LIST，百万条每轮 1000 次 LIST，两种模式均
额外 1 次 HEAD。以下时间是各执行的三轮中位数范围，内存是两个进程峰值范围。

- 十万条：全量模式工作集 56.395–56.402 MiB，首条/完成 1.684–1.704 秒；
  分页模式 13.465–13.480 MiB，首条 8.204–8.441 ms，完成 1.584–1.597 秒。
- 百万条：全量模式工作集 465.512–465.590 MiB，首条/完成 16.408–16.619 秒；
  分页模式 110.738–111.043 MiB，首条 9.631–13.062 ms，完成 16.038–16.042 秒。
- 百万条进程 CPU（预热加三轮、包含析构）：全量 7.719–8.031 秒，分页 17.328–17.641 秒。
  因此不能从相近总墙钟时间推导两种实现具有相近 CPU 成本。

分页的首条延迟与较低工作集在两个顺序中稳定，但它的路径历史仍随文件数增长。
这里没有修改生产扫描逻辑，也不把平坦模拟目录的内存差额当作真实作业内存节省保证。
接下来应使用无模拟等待的对照、不同目录深度和取消点，区分路径去重、分配与调度成本。
原始日志、JSON 和采样输出只保留本地；仓库保留复现源代码及此测量说明。

## 无模拟等待与单页去重实验

零等待基线的两次执行共 24 条记录：百万条全量完成中位数 1.31–1.45 秒，
分页 2.08–2.11 秒；包含一次预热和三轮的进程 CPU 分别为 5.25–5.58 秒、
7.75–7.95 秒。去除定时器后仍有分页自身的 CPU 成本，不能只归因于模拟等待。

曾尝试把单页 BTreeSet<String> 换成借用页面路径的 HashSet<&str>，并绕过单条页面集合。
最终用相同测试源、Cargo 特性和 release 配置分别构建基线与候选；冻结二进制并校验哈希。
四次独立执行按基线/候选/候选/基线顺序，各运行十万/百万条、两种模式、五轮，
共 80 条正式记录。百万条分页候选/基线的总耗时比为 0.985 和 1.057，
CPU 比为 1.014 和 1.043；十万条总耗时比为 0.964 和 0.960，CPU 比为 1.000 和 0.952。
未修改的全量路径也存在波动。首条耗时没有稳定改善，未测量逐操作 p99。

另以 200 ms 持续预热、五批交替顺序、1/10/100/1000 条、每种模式二十轮收集
1600 条记录。小请求仍有明显批间波动，预热不能消除调度和系统负载影响。
因此撤回生产集合替换，保留原实现；只保留顺序/目录别名回归和可复现测量工具。
构建完成前误复制旧程序的一组预备测量已作废，未计入上述结果。

`obs-rust-core/examples/listing_membership.rs` 可通过
`cargo run --release -p obs-rust-core --example listing_membership` 单独比较四种集合的
构造、插入和析构，使用固定唯一键、一次预热与五轮记录，输出 CSV。
其局部 ns/key 收益不能代替完整文件系统测量；集合哈希随机化、分配器和调度仍影响结果。
