# 追加基准：隔离模拟存储扫描和全局锁

2026-10-11。本轮优化测试后端并修正吞吐口径，生产协调器、预算、缓存回调、任务派发和公平队列均未改动。收益是基准去除模拟器干扰的收益，不能当作真实 OBS/PFS 服务端或生产代码的加速比。

## 实现和控制变量

旧 MemoryStore 保留为 legacy 参考组；它的对象表实际为 BTreeMap，上轮报告误写为 HashMap，本轮已更正。扫描仍是遍历所有键并过滤，性能判断不受这个名称更正影响。

新增仅编译进 filesystem 测试的 BenchmarkStore，三组共用相同的数据结构和实现：

- scan-global：全量扫描，同时用一把全局门锁串行化 list 和 append。
- range-global：BTreeMap 下界定位＋连续前缀范围查询，保留同一把全局门锁。
- range-object：相同范围查询，移除 list/append 全局门锁，追加只锁目标对象。

新后端用 RwLock<BTreeMap<String, Arc<Mutex<Bytes>>>> 保存命名空间；追加只在查找时短暂持读锁，释放后操作目标对象。rename 在命名空间写锁下移动对象引用。对象内容快照仍使用 Bytes 的共享与写时复制。list 的目录锁可与无关对象追加并行，读取匹配对象大小时仍锁对应对象。命名空间写锁和同名对象竞争并未消失。

该后端专供这里的文件追加/重命名工作负载；它不是完整 PFS 模拟器。分页请求、超出单页的结果及不支持的 MPU、目录创建、truncate 等 API 显式报 Unsupported。没有故障注入、调用日志和网络时延。legacy 与新后端还存在调用日志、copy+delete/引用移动等差别，因此不能把 legacy→新后端的全部差异归于锁；三组新后端之间才是扫描与锁粒度的受控比较。生产路径仍经过 ObsFileSystem、共享预算、协调器、PfsAppendStream、任务派发和缓存失效。

## 测量口径

4 个 Tokio 工作线程、4 个追加流，每流 250 次 4096 字节 write+flush；保留 32/8192 流，重命名另一个文件 200 次或不重命名。每进程一轮预热＋三轮记录，三批轮换后端执行顺序，每条件 9 个样本，共 576 条纯性能记录。冷/热索引、动态增长/提前预留容量均覆盖。预留只改变模拟数据缓冲区，写入的数据量和最终字节断言不变。

- payload_mib_s 延续旧口径：3.90625 MiB 除以混合负载全部结束时间，包括重命名收尾和流 close。
- append_active_mib_s：同一负载字节数除以最后一次 write+flush 完成时间（从屏障前开始计时），不包含追加结束后单独等待重命名的时间。
- p99 为每轮 1000 个追加操作的 p99，再报告多轮中位数；不是合并所有样本的 p99。不同指标独立取中位数，不能从两个中位数反推另一个。

## 对照结果

以下依次为“混合负载 MiB/s / 追加完成 MiB/s / 追加 p99 μs”，均为无探针中位数。先列重点的 8192 流、预热、200 次重命名：

- 动态增长，legacy：199.84 / 813.65 / 244.7。
- 动态增长，scan-global：218.63 / 813.43 / 218.5。
- 动态增长，range-global：644.60 / 1181.85 / 187.9。
- 动态增长，range-object：846.83 / 2125.50 / 60.2。
- 预留容量，legacy：214.02 / 1152.66 / 154.5。
- 预留容量，scan-global：244.99 / 1362.06 / 145.2。
- 预留容量，range-global：831.65 / 2070.08 / 34.8。
- 预留容量，range-object：997.05 / 3796.90 / 13.1。

range-object + 预留容量：8192 流、冷索引时追加完成吞吐 1386.42 MiB/s，预热后 3796.90 MiB/s；冷启动首次建索引仍会拖慢整批追加的完成时间，却可能因只影响少数操作而不反映在 p99。无重命名的热索引组追加完成吞吐为 3711.40 MiB/s、p99 11.7 μs，说明有重命名组轻微高于该组的吞吐也包含运行波动，不能宣称重命名能加速追加。

完整每轮值和所有 32/8192、冷/热、容量、重命名组合见 JSON；没有丢弃慢样本，没有给出统计显著性或最优性能保证。

## 剩余耗时的分解

启用 append-diagnostics 与 OBS_APPEND_PROFILE 后另外测量热索引矩阵：两批、每条件 6 轮，共 192 条记录/192000 次追加；诊断数据不与无探针结果混算。以下耗时百分比按每轮最慢 10 次操作合并计算。

- 8192 流、预留容量、200 次重命名：scan-global 每轮检查约 1683662 个键，list 持锁累计中位数约 10.391 ms；range-global 约 101 个键、0.056 ms；range-object 约 103 个键、0.054 ms。下界查找成本不计入“检查键数”，但仍在耗时内。
- 同条件的存储锁等待占尾部总耗时：scan-global 83.7%，range-global 28.3%，range-object 0.3%。这些是诊断构建的数据，而非无探针 CPU 采样结果。
- range-object 动态增长容量时，最慢 60 次操作中 58 次自身发生容量增加，持对象锁阶段占尾部总耗时约 92.1%；扩容、数据复制和持锁期间的操作系统抢占仍算在这一区间。
- range-object 预留容量后，任务分段占比为：准备 9.0%、派发 19.7%、服务 26.6%、清理 7.1%、返回/JoinHandle 37.6%。这让生产路径中预算/协调、派发、失效回调和完成通知等开销变得可见，但本轮分段不足以进一步分离每个组件。

所有模拟存储请求均一次 poll 完成；真实网络 I/O 不具备这个特征。派发区间包含 spawn 和调度，返回区间还包含诊断记录写入，不能直接据此删掉生产异步任务或公平队列。探针有分配、时钟读取和锁开销，当前结果用于选择后续检查方向，不能宣称这些百分比等于默认生产构建的瓶颈份额。

## 测试与复现

新增三项测试覆盖：三组存储模式下预留容量、快照独立性、空洞补零、覆盖写、复制、重命名、ASCII/Unicode 前缀边界和超范围请求拒绝；持有一个对象锁时，无关追加和前缀探测仍完成；通过真实 ObsFileSystem 进行覆盖重命名后，原流随路径移动，被覆盖的旧流拒绝继续写入。全量现有公平性、取消、活动追加与重命名测试仍运行。

默认 Rust 297 通过、诊断构建 299 通过，各 11 ignored；JNI 冒烟通过；Hadoop 279 通过、12 跳过、零失败/错误。日志在工作区 work/append-isolation-{rust,features,jni,hadoop}.log。

构建 release filesystem 测试后，运行 scripts/benchmark-append-isolation.ps1 -FilesystemExe <测试可执行文件绝对路径> -OutputDirectory <独立日志目录> -Batches 3。脚本轮换四后端，覆盖全部控制变量，保存并恢复调用者的环境变量；拒绝覆盖已有同名日志，检查每次运行的样本数。-Profile 必须传入启用 append-diagnostics 构建的测试可执行文件。脚本的 Profile 模式默认覆盖冷/热，本轮报告中的剖析仅取热索引矩阵，原始工作区脚本保留在 work/benchmark_append_isolation.ps1。

单项运行设置 OBS_APPEND_BENCH_STORE=range-object 和 OBS_APPEND_BENCH_INPLACE=1；其它控制变量仍为 OBS_APPEND_BENCH_PREWARM、OBS_APPEND_BENCH_RESERVE、OBS_APPEND_BENCH_NO_RENAME，变量存在即启用。未选择 STORE 时继续使用 legacy，便于与历史结果衔接。
