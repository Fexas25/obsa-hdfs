# 首次索引与任务完成集合：独立候选对照

2026-10-11。按“只保留稳定收益”的要求，本轮三个生产候选均撤回。协调器和追加流生产源码与本轮开始时 SHA256 完全一致。保留新增的批量完成基准，以及先完成首个请求、随后两次取消 flush 的回归测试。

## 候选和实验设计

- index：HashMap 的固定索引键从 String 改为 Box<str>。建索引/注册/rename 更新时转换，查找使用 &str；条目载荷由 48 降到 40 字节，槽位值仍是原来的单槽/多槽表示。没有添加多槽堆间接层，也没有把条目大小当作 RSS。
- notify：VecDeque<JoinHandle> 改为 Tokio JoinSet，利用就绪队列取得已完成请求，仍保留句柄所有权、失败后的中止和 flush 排空。
- adaptive：一个直接 JoinHandle 保存首个请求，额外并发请求交给 JoinSet；单请求不进入就绪队列。每次最多先轮询首个句柄，再访问完成队列，保留后续失败可见性。

三个候选独立对照原实现，没有叠加测试。每个实验五批交替执行先后顺序，每进程一轮预热＋三轮记录，每条件每侧 15 次。完整流使用 range-object 隔离模拟后端、Tokio 4 工作线程、4 个写入流、每流 250 次 4096 字节 write+flush、200 次无关文件重命名，覆盖 32/8192 流、冷/热索引和增长/预留容量，共 720 条记录。无时序探针，不与构建或其它测试并行。

索引另有 800 条微基准：32/8192 流，每路径 1/2/4/全部流，每条件每侧 50 条。通知另有 180 条批量基准：4 流，每流写入 1024 个 4096 字节请求，以 1/16/64 次写入为一批，然后 flush；预留最终容量，最大并发配置为 64。实际同时在途数受完成速度影响，不能把批次大小解释为始终有同样数量的在途请求。批量 p99 衡量整批 write+flush，不是单次请求尾延迟，不能跨不同批大小直接比较。

## 批量任务完成结果

以下为各自实验的原实现→候选：混合任务完成吞吐 MiB/s / 整批 write+flush 的 p99 μs。不同实验的基线不混合，不把跨实验数值变化解释为候选收益。

- notify，每批 1 请求：3911.79 / 11.4 → 3349.17 / 11.9。
- notify，每批 16 请求：3229.45 / 177.1 → 3529.90 / 160.3。
- notify，每批 64 请求：2281.90 / 819.6 → 2517.35 / 768.7。
- adaptive，每批 1 请求：3465.60 / 11.4 → 3855.79 / 10.3。
- adaptive，每批 16 请求：3715.14 / 157.1 → 3697.28 / 138.7。
- adaptive，每批 64 请求：2425.97 / 719.0 → 2725.77 / 653.7。

纯 JoinSet 在 16/64 批次有收益，但单请求批次吞吐约下降 14%；adaptive 改善了这项批量基准的单请求表现，却在完整流中出现退步，例如 8192 流、热索引、预留容量吞吐 3546.62→3167.32，p99 13.0→14.9 μs。因此不因局部基准改善而替换生产任务集合。没有给出统计显著性结论，也不声称所有变化都由候选造成；这些结果不足以满足稳定收益门槛。

## 公平性、取消与验证

index 候选通过 25 项协调器回归；notify、adaptive 各通过 32 项追加相关回归，包含后续失败中止前面的慢请求、取消 flush 后恢复、预算等待中失败、重命名公平性等。最终恢复原实现后运行完整回归。

新增 append_cancelled_flush_retains_later_task_after_first_completed：首个请求已提交，第二个请求停在受控门闩；轮询并取消 flush，继续提交第三个请求；第三个提交后再次轮询并取消 flush，最后释放第二个请求并 close。验证完整内容和存储活动字节归零。该新测试针对最终保留的原实现运行，补齐首个任务先完成、仍有后续任务时的取消覆盖。

最终默认 Rust 299 项通过、诊断构建 301 项通过，各 12 ignored（本轮新增一个性能基准）；JNI 冒烟通过，Hadoop 279 通过、12 跳过、零失败/错误。生产索引、通知与取消语义均保持原样。

## 数据有效性与复现

新增批量基准最初误用相对文件系统路径，出现 NoSuchKey，已修正为 /file-N；失败不计入结果。恢复基线源码时，Copy-Item 保留较早时间戳，Cargo 曾复用候选构建，SHA256 检查发现两侧二进制相同；该批记录已整体作废并归档到 work/append-next-invalid-cache-run。随后更新时间戳触发真实编译，确认基线与候选哈希不同后，重新完成全部通知对照。冒烟运行也不计入结果。

索引实验使用 work/append-next-base-initial.exe 作为完整流基线、append-next-core-base.exe 作为微基准基线；通知和 adaptive 使用重建后的 append-next-base.exe。索引实验未运行有路径错误的批量基准，不受该设置错误影响。JSON 为每条结果明确记录所属二进制及校验值。

批量基准可通过 release filesystem 测试可执行文件运行：--exact append_latency::benchmark_append_completion_batches --ignored --nocapture；没有 HTTP/JNI/真实云端 I/O。完整流仍使用上一轮 scripts/benchmark-append-isolation.ps1 或相同环境变量。工作区 work/benchmark_append_next.ps1 保存候选对照流程，work/summarize_append_next.py 保存按独立实验分组的统计，归档候选源码和二进制也在 work/。
