# 追加与重命名本地性能基准

本页保留注册表优化时的历史测量。随后已修复连续 rename 越过等待追加的公平性问题；
公平排队首次测量见 [APPEND_FAIRNESS.md](APPEND_FAIRNESS.md)，最新通知优化见 [APPEND_WAKE.md](APPEND_WAKE.md)。下述未解决公平性
描述对应修复前状态，不代表当前排队规则。

2026-10-11；Windows x86_64、i7-12700H（20 个逻辑处理器）、Rust 1.98.1，release 构建。
本报告测本地协调器和内存模拟存储，不涉及 HTTP、JNI、真实 OBS/PFS、磁盘、TLS 或 RSS。
原始 72 行试验记录、24 组汇总、环境和源码 SHA256 见
[append-rename-20261011.json](benchmarks/append-rename-20261011.json)。

## 重现

在 Windows 项目根目录运行 `./scripts/build-windows.ps1 -BenchmarkAppend`。
其他已配置工具链运行：

```text
cargo test --locked --release -p obs-rust-core benchmark_append -- --ignored --nocapture --test-threads=1
```

协调器默认 4 个追加任务；设置环境变量 `OBS_APPEND_BENCH_WORKERS=64` 可运行本报告的
64 任务场景（接受 1–256）。Tokio runtime 固定 4 个工作线程。该变量不改变完整文件系统
基准：后者始终是 4 个追加任务。清除环境变量可回到默认。两个基准显式 ignored，不把
机器时序数值作为 CI 门限。基准失败、数据错误或请求错误会使测试失败，不输出伪造零值。

每个进程先预热一轮不报告，再运行三轮；每轮轮转场景顺序。操作采用闭环负载：完成
一次才发起下一次，不模拟开放到达率或过载排队。百分位用单次完整操作耗时的 nearest
rank；汇总是三个试验统计量的中位数/范围，不是把不同轮次样本合并后的百分位，也不是
置信区间。吞吐分母为整个并发批次的墙钟时间，包含等待所有任务结束；append_ops_s 和
rename_ops_s 不代表两类请求各自处于活动状态时的最大速率。

协调器层：32/1,024/8,192 个注册流，4 个或 64 个追加任务，每任务 1,000 次请求许可
获取、模拟服务和释放；另一个任务完成 200 次来回重命名。正常场景用 yield 模拟异步
服务；另测设置为 1 ms 的 sleep。8,192 流覆盖不同文件、所有流同一文件、整目录移动。
注册耗时单独记录，不计入吞吐区间；操作计时含协调等待、模拟服务及完成路径。
计时含许可管理但不复制文件内容，因此协调器 ops/s 不能换算成真实数据吞吐。

完整 Rust 路径：32/8,192 个打开流，只有 4 个流实际执行各 250 次 4 KiB write + flush，
另一个任务执行无关文件的 200 次来回 rename。包含分配、复制、Tokio 任务、缓存失效
和 MemoryStore 调用；逐字节验证最终内容与文件名。大量流场景主要考察注册表规模，
不是 8,192 个并发网络请求。MemoryStore 在全局对象锁内复制已存储的完整文件，且有
全局调用记录锁，这是测试替身的成本，不能据此推断生产 OBS Store 的锁或复制行为。

## 本轮改动与四任务对照

基线为按路径范围协调、但每次注册扫描所有弱引用、重命名逐个锁住目标的版本。
优化将注册表弱引用清理改为几何阈值触发，摊销连续注册的扫描成本；注册表缓存路径，
重命名先过滤范围，再升级弱引用/取得相关目标锁。成功移动同步更新两份路径；既有
取消、覆盖目标、目录后代保护保持。新增流高频创建/释放回归检查弱引用回收与存活流。

以下均为同一负载三轮统计量的中位值，完整范围见 JSON：

- 8,192 个不同文件，协调器：注册总耗时 75.49 → 8.07 ms；混合批次追加吞吐
  17,103 → 106,002 ops/s；追加 p99 1.802 → 0.200 ms；重命名 p99 2.305 → 0.376 ms。
- 1,024 个不同文件，协调器：追加吞吐 116,985 → 282,300 ops/s；重命名 p99
  0.630 → 0.220 ms。
- 8,192 流同文件：追加吞吐 8,561 → 8,828 ops/s，重命名 p99 4.298 → 3.831 ms；
  没有多文件场景那样的改善。目录移动追加吞吐 6,373 → 5,914 ops/s，重命名 p99
  5.151 → 6.045 ms，本次结果未改善，不能宣称全场景提速。
- 8,192 个打开流的完整内存存储路径：实际负载吞吐 11.14 → 17.71 MiB/s；
  write + flush p99 6.184 → 3.910 ms；rename p50 0.535 → 0.141 ms，但 rename p99
  2.951 → 6.543 ms。优化后三轮 rename p99 范围为 0.668–13.280 ms，不能忽略退化。
  后续 64 任务基准进程中重跑的完整流基准仍为四任务，rename p99 三轮为
  0.412–0.477 ms、中位 0.420 ms。这说明尾延迟对本机调度/模拟锁竞争敏感，不能选择
  最好一批作为稳定保证；更多隔离重复与锁等待剖析仍有必要。

## 64 任务压力结果与剩余瓶颈

这里每轮追加操作数为 64,000，四任务是 4,000，不能直接把两组吞吐比解释为扩展效率。
8,192 个不同文件：追加吞吐中位 527,788 ops/s、追加 p99 1.012 ms、重命名 p99
0.592 ms。所有流同文件时重命名 p99 为 5.263 ms，目录移动为 6.405 ms。

- 同文件与目录整体移动仍需更新大量相关目标，缓存路径不能消除这项线性工作，且增加
  一份路径元数据。全部目标都相关时，额外路径维护可能抵消收益，未测新增 RSS。
- 连续重命名可能多次抢在被唤醒的追加之前登记范围，当前没有对追加给出有界等待
  保证。64 任务同文件和目录场景的每轮最大追加延迟中位分别约 333 ms、380 ms；
  这比对应 p99 大得多。低 p99 不等于没有长停顿，后续应优先验证公平排队。
- 协调状态仍有短时共享互斥锁；范围查找仍是线性扫描，并使用共同的 Notify 唤醒。
  本轮没有分离测量这些成本，不能仅凭吞吐数字给它们分配 CPU 占比。
- 1 ms 模拟 sleep 的实测请求尾延迟通常接近 16–17 ms，反映此 Windows 环境的计时/
  调度粒度，并不是 1 ms 云端 RTT 的性能结果。64 任务该场景最大追加延迟的轮次中位
  约 863 ms，需结合重命名公平性和调度开销进一步定位。
- 字节预算、HTTP 连接池及真实服务还会增加背压；本次没有启用真实服务，也未测 Linux。

弱引用清理是惰性的：到达几何阈值的注册或重命名完成会清理过期条目；无后续活动时
部分过期弱引用及缓存路径可保留到文件系统释放。元数据不属于 payload 预算，不能把
本次结果称为完整内存上限或无开销优化。
