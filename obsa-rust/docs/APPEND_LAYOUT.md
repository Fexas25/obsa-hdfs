# 容量复用：索引布局、模拟存储锁和调度对照

2026-10-11。本轮没有保留生产性能改动：缩小索引桶的候选收益不稳定，已经撤回。协调器与本轮开始时 SHA256 完全一致，公平排队、取消和定向通知保持原样。保留了诊断开关、扩容/扫描计时和确定性回归测试。

## 方法与可复现范围

本地 Windows release，Tokio 4 工作线程，4 个追加流，每流 250 次 4096 字节 write+flush；同时保留 32 或 8192 个流，重命名无关文件 200 次。每次进程运行先预热一轮，再报告三轮；三批交替 before/after 顺序，每个条件每侧 9 个样本。矩阵含冷/热索引、动态扩容/预留容量、200/0 次重命名，共 288 组完整流记录。这里的 p99 是各轮 1000 次操作 p99 的中位数，不是合并所有操作的 p99。

索引独立微基准覆盖每路径 1、2、4、全部流，共 480 条记录。候选只把 Many(Vec<usize>) 改为 Many(Box<Vec<usize>>)，并在第二个槽位插入时 Box::new。实际测量槽位值 24→16 字节（不能凭源码猜成 32→16），String+槽位元组 48→40 字节。这不是 RSS 测量，多流路径多一次堆分配。

## 分段诊断

在恢复原布局后单独启用 append-diagnostics/profile，两批、每条件 6 轮，共 96 组、96000 次操作；未与无探针吞吐混算。扩容记录在持对象表锁时采集，list 记录锁等待、持锁区间和扫描对象数，记录写入在解锁之后。预热期间的 list 记录在计时开始前清空。

- 8192 流、热索引、增长容量、200 次重命名：每轮最慢 10 次追加合并耗时中，对象表锁等待约 70.0%，持锁约 16.6%；任务派发约 11.4%，请求前准备约 0.2%。
- 同条件预留容量后：锁等待约 66.8%，持锁约 2.4%，任务派发约 24.8%。这些比例来自不同的分解视角，不能将阶段交叉相加。
- 增长容量每轮有 36 次容量增加；预留条件为 0，且已断言初始容量足够、无转换复制回退。最慢操作不一定自身扩容：它也会等待其他流扩容。
- 预热且有重命名时，每轮目录探测扫描约 202–211 次，扫描 8193 个对象；增长容量条件 list 累计持锁中位数约 12.165 ms。预留容量后，尾部操作锁等待时间约 70.0% 与 list 持锁区间重叠；增长容量时该重叠约 10.0%。
- 无并发重命名时，计时区间 list 扫描为 0。8192 流、预热、原布局的无探针对照：增长容量吞吐 200.81→1099.42 MiB/s（移除重命名负载）；预留容量且保留重命名时为 221.17 MiB/s、p99 132.0 μs。改变负载/存储模型的结果不是生产加速收益。

更正：模拟存储以 BTreeMap 保存对象（先前误写为 HashMap），list 对不存在的目标目录探测会持全局对象表锁扫描所有键，追加扩容也持同一把锁。预热消除了首次建索引，却没有消除这些成本。存储请求在本轮均单次 poll 完成，不能据此排除操作系统抢占：同步 Mutex 等待会阻塞工作线程。派发区间还包含 spawn/排队等成本，不能全部归因于 Tokio 调度器。本轮不能解释历史某两次 p99 变化的全部原因，也没有测量真实 OBS/PFS 服务端表现。

## 保留改动与验证

- 新增 OBS_APPEND_BENCH_RESERVE（必须同时 INPLACE），仅给四个模拟写对象预留最终容量，长度保持 0，并验证 freeze/try_into_mut 不丢容量。
- 新增 OBS_APPEND_BENCH_NO_RENAME；空样本分位数返回 count=0，避免访问空切片。
- 逐操作记录容量前后值和 copy_fallback；回退也包括静态空 Bytes，不能直接解释成非空共享快照复制。历史测量 JSON 字段名 shared_fallback 保留，并在元数据中说明。
- 新增测试验证空长度预留容量复用、共享快照独立性、扩容、间隙补零、覆盖写入与扫描计时。
- 默认 Rust 294 通过、11 ignored；诊断构建 296 通过、11 ignored；JNI 冒烟通过。Hadoop 279 通过、12 跳过，零失败/错误。

复现：用 scripts/build-windows.ps1 的 MSVC 环境构建 release filesystem 测试；运行该测试可执行文件 --exact append_latency::benchmark_append_filesystem --ignored --nocapture。设置 OBS_APPEND_BENCH_INPLACE=1；分别组合 PREWARM、RESERVE、NO_RENAME（均带 OBS_APPEND_BENCH_ 前缀），变量缺省关闭，值为 0 仍表示启用。剖析另加 OBS_APPEND_PROFILE=1 并以 --features append-diagnostics 构建，不能与纯性能结果混合。索引微基准运行 core 单测可执行文件 benchmark_append_index_build --ignored --nocapture。所有计时单独运行，避免构建和其他基准竞争。
