# 追加 p99 分段诊断与对照

后续索引分配优化与存储任务分段见 [APPEND_INLINE.md](APPEND_INLINE.md)；本页保留历史结果。

2026-10-11。继续调查上一轮默认模拟存储中追加 p99 从 4.56 到 6.41 ms 的变化。
核心保持纯 Rust，公平协调队列和惰性路径索引均未改动，Hadoop/JNI API 不变。

## 结论与证据边界

本轮直接重建索引引入前的版本，与现有索引版使用相同的逐操作观察工具和基准负载。
冷索引、8192 流、默认模拟存储下再次出现 p99 上升：4.508 → 5.848 ms；两组范围明显
重叠。容量复用诊断下，p99 为 0.278 → 0.269 ms，吞吐为 113.09 → 177.88 MiB/s。
不能认为上次退步已经消失，也不能把 1.85 ms 差值全部归因于索引构建。

逐操作证据将主要瓶颈定位到测试 MemoryStore 的全局对象锁及锁内整文件复制。
索引版冷启动三轮各最慢 10 次追加（共 30 次）的总耗时中，对象锁等待占 83.9%，
持锁占 7.0%；这些慢操作均发生在每个流的第 74–246 次操作（从 0 开始编号），
不是开头的首次建索引。预热后最慢 30 次的锁等待仍占 80.9%。旧版冷启动相应等待
占 77.5%。这些百分比是该组尾部操作的累计延迟占比，不是 CPU 利用率。

默认测试每轮有效载荷只有 3.90625 MiB，但在同一对象锁中显式复制 486.328125 MiB
旧前缀。同步 Mutex 等待也占用 Tokio 工作线程，可能影响其它任务的调度。
减少协调器扫描会改变任务到达这个共享临界区的时序；这可以解释瓶颈转移的方向，
但现有观察不能严格量化它对历史两次 p99 差值的因果贡献。分配器、OS 调度及系统负载
仍会影响尾部，未进行内核调度或 CPU 采样。

首次构建索引确实有同步持锁成本：独立 release 微基准中，8192 个不同路径的构建
中位数为 1.681 ms（1.629–1.743 ms），8192 个同名流为 0.475 ms。微基准无竞争，
只测 ensure_exact_index 的锁内执行时间；不能把这个数当作完整流中的锁等待。
完整流预热使用两次真实文件 rename，包含元数据、存储等额外开销，并非纯索引计时。
容量复用的冷启动尾部更容易看到开头几次追加的 pre_store 开销，预热对照用于将其
与持续阶段区分；默认复制模式中，后半段的共享存储锁仍是主要问题。

## 新增观察能力

OBS_APPEND_PROFILE=1 时，每次追加保留 worker、operation、相对起点及如下纳秒区间：

- pre_store：从 write 开始至存储请求开始，包含预算、协调准入、缓冲准备与任务派发。
- store_setup：模拟存储开始至请求对象锁，包含测试调用记录等准备。
- store_wait：请求对象锁至取得对象锁，是直接测得的对象锁等待。
- store_hold：取得对象锁至释放对象锁后的时间戳，包含复制、增长和对象更新。
- post_store：上述释放点至 flush 返回，包含观察记录、许可释放、缓存回调和继续调度。

五段逐操作严格相加等于总耗时，汇总脚本验证了 48,000 次记录的这一恒等式。
另记录 write 返回时间和写入 Future 的 wake_to_poll 时间：后者使用包装 Waker，
记录第一次唤醒到下一次 poll 的间隔，连续唤醒不覆盖首次时间。它观察写入 Future，
不覆盖内部存储任务全部调度，也不区分 OS 抢占；它与上述区间重叠，不能再次相加。
post_store 不能直接称为纯调度延迟，pre_store 也不能称为纯协调锁等待。

观察器仅在测试代码和显式诊断模式启用，没有增加生产请求的计时或日志开销。
诊断记录按四个写入者分开保存，且在释放模拟对象锁之后写入。观察器仍包含时钟、
包装 Waker 和记录分配成本；带观察器结果只用于定位，性能结论使用关闭观察器的对照。
冷/热索引及容量复用均由独立环境开关控制，默认基准仍保持原整文件复制语义。
所有轮次继续检查文件最终长度和每一个字节。

## 本轮生产改动

追加内部缓存失效回调原先对初始路径和当前路径各调用一次 invalidate；未发生重命名时
两个路径相同。本轮保留第一次失效，仅当路径不同才执行第二次，避免重复获取缓存
失效 epoch 写锁和重复驱逐。任务退出、flush、Drop 的回调触发点均不变。
重命名后仍清除原路径与新路径；没有改变冲突 FIFO、准入、取消或定向唤醒逻辑。

新增确定性测试覆盖立即完成/挂起唤醒的观察器，以及追加前后状态刷新、重命名后
旧路径负缓存与新路径状态同时失效。既有持续 rename 公平性、取消、流改名和缓存
回填竞争测试继续运行。减少重复操作是确定的；完整流性能没有跨场景一致改善，
不将该小改动宣传为解决了 p99。

## 无观察器对照

每个条件 9 个记录轮次，来自 3 个批次；每次进程运行先预热一轮，再记录三轮。
批次交替版本顺序，并轮换 copy/inplace 模式顺序；32/8192 流顺序也轮换。
仍为 Tokio 四工作线程、四个写入任务，各 250 次 4 KiB write+flush，另 200 次无关
文件 rename。下列数值为轮次中位数，括号为 min–max，不是置信区间。
历史实验的 legacy→before 是引入索引的比较；缓存实验 before→after 是本轮小改动。
两个实验中 before 的分布也有变化，不能跨实验直接拼接百分比收益。

## 复现与验证

使用 scripts/build-windows.ps1 -BenchmarkAppend 可构建并运行 release 追加基准。
完整流入口是 append_latency::benchmark_append_filesystem；索引构建入口是
io::append_coordination::benchmark::benchmark_append_index_build。后者独立运行，
不要与编译、其它基准或系统重负载并行。

环境变量按是否存在判断：OBS_APPEND_PROFILE 开启逐操作记录，
OBS_APPEND_BENCH_INPLACE 开启模拟存储容量复用，OBS_APPEND_BENCH_PREWARM 在计时外
执行两次 rename。关闭开关必须移除变量，设置为 0 仍表示开启。
每个独立运行有一轮不输出的预热；随后输出 APPEND_BENCH 或 APPEND_INDEX JSON。

工作目录的 benchmark_append_tail.ps1 与 benchmark_append_tail_history.ps1 保留了
交替运行顺序；summarize_append_tail.py 验证所有数据并导出摘要。
原始日志为 work/append-tail-{paired,history,profile,legacy-profile}-*.log，完整逐操作
轨迹打包于 outputs/append-tail-operation-traces.jsonl.gz，含 48 轮、48,000 次记录。
版本及日志 SHA256、288 条无观察器轮次、尾部样本与分段结果见
[机器可读结果](benchmarks/append-tail-20261011.json)。before/after 发布基准可执行文件
使用相同计时路径；随后补充的独立正确性测试在最终 debug 回归中运行。

验证日志：work/append-tail-rust.log、append-tail-jni.log、append-tail-hadoop.log。
Rust 292 通过、11 ignored（显式性能基准）；JNI 冒烟通过；Hadoop 291 项中 279 通过、12 跳过，零失败/错误。
没有真实 OBS/PFS 桶，以上为本地模拟证据，不代表 HTTP、JNI 或云服务吞吐。

尚未解决：默认模拟存储下 p99 对锁竞争和运行时序的敏感性；首次建索引仍同步持锁；
目录移动会使索引失效，目录/文件交替工作负载尚未补齐；跨实例及真实云环境需要后续验证。
