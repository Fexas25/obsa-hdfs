# 首次索引和完成路径：热点定位

2026-10-11。本轮先增加可关闭的诊断，再验证候选。没有保留生产性能改动；公平排队、预算获取顺序、任务所有权、取消和通知方式保持原实现。保留索引组件探针、完成扫描聚合计数、批量基准的诊断接入及取消回归断言。

## 实验范围与可复现性

所有运行在本地 Windows、release 模式、同一机器串行执行，不与构建/测试重叠。完整流和批量追加使用 range-object 隔离后端（范围查询、逐对象锁），没有 HTTP/JNI/真实 OBS。完整流为 4 个写入流、32/8192 个注册流、每流 250 次 4096 字节 write+flush、200 次无关文件重命名。批量基准为每流 1024 次请求，批大小 1/16/64 后 flush，预留最终容量。批大小不是恒定在途任务数。

- 索引组件探针：五个进程，每条件十次记录，轮换预留/增长构建顺序，共 800 条。每路径 1/2/4/全部流，所有条目存活，短文件名。
- 完成扫描诊断：五个进程，每进程一轮预热＋三轮记录，45 条批量记录、30 条热索引/预留容量完整流记录，后者包含 30000 次逐操作分段。
- 避免重复键克隆候选：五批交替原版/候选先后顺序，240 条无探针完整流结果，800 条索引微基准。每条件每侧完整流 15 次、索引 50 次。
- 合计 1915 条顶层记录。原始数据和可执行文件 SHA256 保存于 [JSON](benchmarks/append-hotspots-20261011.json)。候选与基线可执行文件哈希不同；恢复源码后更新时间戳，避免 Cargo 复用旧候选产物。

完成计数仅在 `append-diagnostics` 特性启用且附加 sink 时记录；每个 sink 新增 6 个固定大小原子计数器。输出 `completion_scans` 为每个写入流的 `[reap_calls, reap_handles, reap_ns, join_polls, join_handles, join_ns]`，读数在流关闭后取快照。它们覆盖整个流生命周期，包含 close，不是逐操作独立分段。纳秒字段是计时单位，不能当作计时器具有纳秒精度。计时包括调用时钟的开销，不含写入聚合计数器的开销；计数更新和已有任务探针仍会改变调度，不能把诊断吞吐当成无探针吞吐。

## 首次索引

8192 条目的中位数（微秒），依次为遍历、克隆、单次哈希探针、预先克隆键后的插入、完整增长构建、完整预留构建：

- 每路径 1 流：35.40 / 365.45 / 92.10 / 959.95 / 1361.70 / 1069.80。
- 每路径 2 流：36.35 / 393.45 / 94.05 / 770.35 / 1088.40 / 1186.45。
- 每路径 4 流：33.10 / 346.10 / 90.65 / 648.85 / 894.20 / 1092.95。
- 每路径 8192 流：25.85 / 351.20 / 83.70 / 334.05 / 518.60 / 516.80。

这些组件是独立探针，**不能相加或据此推算 CPU 百分比**：预先分配键改变缓存局部性和分配器状态，单独哈希也不包括增长重哈希。证据支持把注意力放在键分配、插入和扩容，而非存活检查遍历。

直接按流数预留容量仅在独立路径明显改善。8192 流每路径 2/4 流反而变慢；全部同名时容量从 3 升到 14336，而构建耗时基本不变。这种预留策略未进入生产代码，未把微基准改善宣称为端到端收益。

## 完成路径

每条件 15 轮，以下为每轮值的中位数。逐次 write+flush 时，完整流每 1000 请求发生 2000 次空 reap 检查、2000 次 join 轮询、2000 次句柄检查。32/8192 流的扫描计时总量分别约 0.210/0.209 ms；跨全部对应操作累计计算约占操作总时间 3.92%/3.90%，包含计时开销和生命周期范围差异。这不支持把单请求路径的较长完成等待主要归因于队列长度。

批大小 1/16/64 时，总句柄检查次数除以请求数的逐轮中位数分别为 2.00/32.34/120.01。批量 64 时，reap 扫描约 0.653 ms、join 轮询约 3.706 ms/4096 请求，扫描确实随批量放大。批量 p99 是整批时间，不能按单请求解释。

8192 流完整路径，按所有操作耗时加权的 prepare/dispatch/service/cleanup/join 分别约 16.7%/14.9%/38.7%/7.4%/22.3%。每轮最慢 1% 操作（共 150 次）分别约 11.2%/18.9%/26.7%/18.2%/24.9%。join 包含任务记录完成之后的运行时唤醒、调度及 flush 尾部工作，cleanup 包含 permit 释放、回调及调度中断，不能把这些百分比等同于某一个函数的 CPU 占比。尚未用采样剖析器分离缓存回调和运行时内部热点。

上一轮 JoinSet 替换没有稳定端到端收益，本轮没有再次据批量扫描次数直接替换通知机制。

## 针对性候选与取舍

候选在首次建索引时先 `get_mut(&str)`，仅首次出现的路径克隆并插入键，减少重复路径分配；代价是独立路径多一次查找。其余路径不改。协调器 25 项回归通过。

- 32 流，每路径 1 流：3.90 → 4.40。
- 32 流，每路径 2 流：3.60 → 3.20。
- 32 流，每路径 4 流：3.30 → 2.40。
- 32 流，每路径 32 流：2.50 → 1.20。

- 8192 流，每路径 2 流：1100.40 → 929.30。

- 32 流，冷索引，预留容量：2802.99 / 17.7 → 3527.09 / 14.1。

重复路径微基准改善明显，但 32 个独立路径在五批中均变慢；8192 独立路径方向随批次变化。完整流也未得到稳定改善。热索引负载的计时区间不调用修改过的建索引分支，其差异是运行噪声/构建布局等因素的信号，不能直接归因于建索引算法。本轮撤回候选，避免用某个条件的好结果替代稳定性验证。

## 回归与复现

增强现有诊断回归：在后端被确定性门闩阻塞时，轮询一次 flush 然后取消，验证恰好新增一次 join 轮询和一次句柄访问，reap 计数不变；随后分别验证成功、失败和流丢弃中止。聚合 sink 的单元测试覆盖零初值、累加和有界记录丢弃计数。

本轮默认 Rust 299 项通过，诊断构建 301 项通过，各 13 ignored；新增 ignored 项是索引组件基准。没有修改 Java/JNI 接口，本轮未重跑 JNI/Hadoop，上一轮结果仍见 APPEND_NEXT.md。无真实云服务验证。

```powershell
$env:OBS_APPEND_PROFILE='1'

```

纯性能运行前删除 OBS_APPEND_PROFILE，使用未启用诊断特性的构建；环境变量按“是否存在”启用，不要用字符串 0 关闭。候选源码、五批运行脚本、原日志和可执行文件留在授权工作区 `work/hotspots-*`、`work/benchmark_hotspots.ps1`；目标项目中不保留被撤回候选。
