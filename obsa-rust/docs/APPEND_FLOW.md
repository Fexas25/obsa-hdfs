# 完整追加流的瓶颈与惰性路径索引

后续逐操作排查与重跑结果见 [APPEND_TAIL.md](APPEND_TAIL.md)；本页保留上一轮历史数据。

2026-10-11。核心仍为纯 Rust，Hadoop/JNI 接口不变。本轮保留冲突 FIFO 与定向通知，
针对精确文件 rename 的全注册表扫描增加惰性索引；同时测量完整流基准的实际存储开销。


结论：默认完整流的主导开销是模拟存储中的整文件复制和共享对象锁。8,192 流交替
对照的吞吐中位数 17.40 → 18.51 MiB/s，rename p99 5.46 → 2.74 ms，但追加 p99
4.56 → 6.41 ms，仍有退步且区间重叠。不能宣布完整流尾延迟问题已经解决。
容量复用诊断下的吞吐 110.43 → 185.75 MiB/s，显示精确路径索引的收益；目录协调
吞吐约 6.56 万次/秒，保持原水平。较大的 max 与首次建索引成本可能有关，但没有
逐操作调度轨迹，不能把所有极端样本归因于索引或系统调度。

## 瓶颈证据

在测试 MemoryStore 的 posix_append 内可选记录累计总耗时、对象锁等待、持锁时间及
显式旧前缀复制字节，与各次 write+flush 的累计耗时对照。它们是并发操作延迟之和，
包含等待，不是 CPU 占比，也不是进程总墙钟时间占比；未进行 CPU 采样或 RSS 测量。

- 原版 32 流：存储内部占累计追加延迟 97.9%（97.4–98.1%），对象锁等待 72.1%，持锁 25.2%。

- 原版 8192 流：存储内部占累计追加延迟 96.8%（96.8–97.5%），对象锁等待 71.4%，持锁 26.0%。

每轮四个流各执行 250 次 4 KiB write+flush，实际写入 3.90625 MiB，但默认模拟存储
在全局对象锁内每次 to_vec 复制旧文件，显式旧前缀复制总计 486.328125 MiB，即有效
载荷的 124.5 倍。另有 Vec 增长/分配器潜在复制，计数未覆盖。该行为属于测试存储，
不是 Rust OBS 客户端每次追加都会复制整个远端文件。

原基准低吞吐和高尾延迟主要受这个共享临界区影响。容量复用诊断模式在保持最终内容、
偏移和快照语义的前提下移除显式整段 to_vec，用来观察其他开销；它不代表真实 PFS。
计数为零只代表未走显式旧前缀复制分支，不代表 BytesMut 增长或共享快照回退没有复制。
容量复用后，原版 8,192 流仍明显慢于 32 流；精确文件 rename 的两次全注册表扫描
由代码路径确认，是本次生产优化目标。时钟/线程调度异常不能仅由上述累计计时解释。

## 最终实现与公平性

保留原 Vec 注册表与目录更新路径，只有精确文件 rename 需要时才构建路径到槽位列表
的 HashMap。后续文件 rename 只检查源/目标对应的流；首次构建仍为 O(N)，之后索引
有效时平均查询 O(1)，相关流检查/更新 O(K)，冲突队列查找仍为 O(Q)。

注册新流时更新有效索引；几何阈值清理会压缩 Vec 并使索引失效。目录移动沿用原线性
更新并丢弃索引，下次文件 rename 按需重建。先移除源和目标的旧索引桶，再处理相关
槽位，避免刚移动的源流又被当作覆盖目标失效。同名多流、已有失效流和取消保护保留。
精确 rename 只从索引移除过期引用，Vec 中死弱引用槽位等待注册清理或目录更新压缩。

没有改变冲突 FIFO 和通知依赖。后来的 rename 仍不能越过已经登记的追加；目录操作
与无关文件仍按原范围规则协调。索引属于额外元数据，不在有效载荷内存预算内。

曾测量全路径分组表候选：64 任务目录移动吞吐从约 63,097 降至 19,144 次/秒，追加
p99 从 7.298 升至 23.362 ms，因此放弃了该候选。证据保留于
[候选完整原始结果](benchmarks/append-flow-grouped-20261011.json)。

## 对照方法

普通运行仍使用 `./scripts/build-windows.ps1 -BenchmarkAppend`。可设置
`OBS_APPEND_PROFILE=1` 开启完整流存储计时；`OBS_APPEND_BENCH_INPLACE=1` 开启容量复用
诊断。未设置这两个环境变量时保持默认复制模拟路径。性能对照先清除这两个变量，
按所需诊断模式单独设置；`OBS_APPEND_BENCH_WORKERS=64` 仅改变协调器任务数。

完整流 before/after 使用同一测试存储与基准源码，关闭计时插桩，交替可执行文件先后
顺序，三批，每批一轮预热和三次测量，每版本每流规模九次计时；默认复制与容量复用
诊断分别进行。完整流仍只有四个写任务。测量结束核对所有最终文件内容及 rename 结果。

协调器单独测 64 任务，使用未修改的原基准源码，预热一轮后轮转场景三轮；新旧按块
顺序执行，非随机配对 A/B。报告中位数与范围均来自每次试验的统计量，不是合并样本
百分位。机上波动、序列效应仍存在，不把每个百分比都解释成纯代码贡献。
原始试验、源码/可执行文件 SHA256 见
[append-flow-20261011.json](benchmarks/append-flow-20261011.json)。

## 仍需处理的边界

默认模拟存储仍具有全局对象锁和整文件复制，保持它可以持续观察端到端瓶颈，不能将
更快的诊断存储替换后直接宣称产品加速。缓存失效、任务调度和真实 HTTP/TLS 请求仍
需独立数据；目前没有真实桶、Linux、CPU profile 或 RSS 验收。

文件 rename 第一次查询和目录移动后的第一次查询仍需建立全表索引；频繁交替目录与
文件 rename 可能反复构建，需要额外混合负载测量。目录移动仍为 O(N)，准入共享锁、
冲突队列扫描和调用方长时间持有许可仍存在。公平准入不提供固定毫秒完成上限。
