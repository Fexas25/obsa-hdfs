# 追加与连续重命名的公平排队

本页保留公平队列首次引入时的测量。后续已优化通知和重复扫描，当前结果见
[定向通知优化](APPEND_WAKE.md)；下列数字属于优化前历史基线。

2026-10-11。本轮修复同一 ObsFileSystem 实例内，连续 rename 越过已经等待的追加，
使少数追加操作反复等待的问题。这里的公平性是冲突请求的准入次序，不是毫秒截止时间。

## 实现与边界

重命名、受阻的追加和受阻的流注册共用有序队列。追加/注册只等待排在自己前面的
相关 rename；rename 只等待排在自己前面的冲突操作以及相关在途追加。多个较早追加
可以并行准入；无关路径可以越过不相交的等待者，因此不恢复全实例网络锁。

追加等待项持有流目标身份，判断冲突时读取其当前路径。更早的目录或文件 rename
成功更新目标后，等待项自动跟随；不会因仍使用旧路径而被后来的 rename 越过。
没有冲突的追加/注册不分配排队项。成功追加准入时，队列依赖转移给在途许可，等请求
完成后通知，省去准入时一次多余的全体唤醒。

排队项使用 RAII 清理：取消、成功、流已失效而报错都会移除；取消未发送的 rename
仍不使流失效，已发送但结果不确定仍保持原来的失效保护。协调状态锁不跨 await/网络
请求；锁顺序仍为协调状态 → 流目标。

保证针对已登记的操作、且相关前序请求能完成/取消、等待任务继续获得调度的条件。
进入协调器之前的字节预算等待、服务端挂起、调用方保留不释放的许可、线程调度停顿
不由此队列给出固定上限。跨实例、带外 rename、直接构造的独立追加流仍不受它协调。

## 确定性验证

新增 7 项普通回归，不以 sleep 长短或性能门限判断公平性：

- 先让追加等待，再完成第一次 rename，优先 poll 后来的 rename，确认其仍 Pending。
- 更早登记的 rename 优先于后来的追加；但再晚的 rename 不能越过该追加。
- 取消等待中的追加移除其队列位置，后续 rename 可完成。
- 目录下多个早到追加全部准入/排空后，后来的目录 rename 才能执行；无关目录仍可推进。
- 流注册也能抵抗后来 rename 插队，取消注册不遗留阻塞。
- 结果不确定导致流失效时，等待追加报错并清理队列。
- 完整 Rust 文件系统路径确认早到 write 完成前，后来 rename 尚未发到模拟存储，
  并验证移动后继续追加的最终字节。

前三项在旧实现确认失败，证据 work/append-fair-before.log；修复后全部通过。

## 相同负载的 release 重跑

命令、场景和计时方法沿用 [APPEND_PERFORMANCE.md](APPEND_PERFORMANCE.md)：1 轮预热、
3 轮测量、轮转场景、固定 4 个 Tokio 工作线程，分别运行 4/64 个追加任务。
64 任务仍每任务 1,000 次追加、共 200 次 rename；完整内存文件系统基准始终四任务。
所有内容/路径断言通过。新旧共 96 行原始试验、32 组统计及源码散列见
[append-fairness-20261011.json](benchmarks/append-fairness-20261011.json)。

基线采用上一轮同机测量，新实现本轮重跑；相同负载、基准源码已核对，没有做随机
交替的配对 A/B，因此机器状态/调度波动不能排除。下述最大值是“各轮最大操作延迟”的
三轮中位数，p99 也是各轮 p99 的中位数，不是汇总全部样本后的百分位。

### 8,192 注册流的热点场景

- 四任务同文件：最大追加延迟 186.37 → 6.32 ms；追加 p99 0.023 → 3.405 ms；
  吞吐 8,828 → 7,103 ops/s。
- 四任务目录移动：最大追加延迟 490.84 → 8.70 ms；追加 p99 0.017 → 5.038 ms；
  吞吐 5,914 → 4,915 ops/s。
- 64 任务同文件：最大追加延迟 332.56 → 17.21 ms，新值各轮范围 11.22–19.42 ms；
  追加 p99 0.323 → 7.489 ms；吞吐 108,883 → 77,137 ops/s；rename p99
  5.263 → 8.440 ms。
- 64 任务目录移动：最大追加延迟 379.61 → 15.17 ms，新值范围 12.11–15.33 ms；
  追加 p99 3.359 → 8.058 ms；吞吐 81,148 → 53,480 ops/s；rename p99
  6.405 → 9.079 ms。

最大停顿明显减少，但 p99 与吞吐不是普遍改善。结果与从少数请求反复等待，变为
冲突请求轮流获得准入的行为一致；不能通过只报告最大值改善，隐藏热点吞吐下降。
这也不是已经证明所有负载都拥有 20 ms 上限。

### 多文件及模拟服务等待

8,192 不同文件：四任务追加吞吐 106,002 → 106,366 ops/s，最大追加延迟
28.25 → 6.76 ms，但 rename p99 0.376 → 1.298 ms。64 任务追加吞吐
527,788 → 756,593 ops/s，最大追加延迟 12.02 → 5.46 ms，rename p99
0.592 → 2.634 ms。不能把这些吞吐变化全归因于公平队列，或宣称没有尾延迟代价。

设置 1 ms sleep 的 64 任务场景，最大追加延迟中位 863.04 → 31.66 ms；实测
p99 仍约 16–17 ms，Windows 定时器/调度粒度限制继续存在，不是云端 RTT 结果。

完整内存存储的 8,192 打开流场景：本轮两批 payload 吞吐中位分别 19.14、17.76 MiB/s，
rename p99 分别 1.301、4.700 ms。模拟存储全局锁、复制增长文件及本机调度导致波动，
不能据此给出真实 HTTP/PFS 性能承诺。

## 仍需改进

- 大目录或所有流共享文件时，更新目标仍是线性工作，公平队列并未消除它。
- 队列和目标表仍线性扫描，Notify 仍存在共同唤醒；高竞争场景队列管理和重调度有成本。
- 缓存路径、等待元数据不属于 payload 内存预算，本轮未测 RSS。
- 本轮没有真实 OBS/PFS、Linux、开放到达率过载测试或 CPU 锁等待剖析。
