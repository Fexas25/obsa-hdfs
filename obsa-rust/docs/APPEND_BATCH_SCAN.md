# 批量追加重复扫描：两个候选的对照

2026-10-11。本轮两个候选均撤回，生产追加实现与本轮开始时逐字节一致。保留可延长的批量基准和两个确定性回归。没有改动重命名公平队列、任务完成通知、预算策略或 Hadoop/JNI 接口。

## 实验设置

隔离模拟后端 range-object，范围查询与逐对象锁；不使用真实 OBS、HTTP 或 JNI。Tokio 4 工作线程、4 写入流、每次 4096 字节。批量追加每流 8192 请求、每进程每条件 128 MiB，批大小为 1/16/64，预留最终对象容量，最大并发配置 64。每批结束 flush；批大小并非恒定在途数。p99 为整个批次的延迟，不能当成每请求 p99。

新增 `OBS_APPEND_BENCH_REQUESTS` 控制每流请求数，默认仍为 1024，范围 64..=16384 且须为 64 的倍数。容量、循环次数、验证长度、诊断记录上限及吞吐分母均使用同一请求数。本轮比旧默认的 16 MiB/轮更长，避免只根据几毫秒短测试得出收益结论。

每个候选五批交替基线/候选先后顺序，每进程一轮预热、三轮记录。每个条件每侧 15 次记录，两个实验使用独立的基线测量，不合并它们。先完成全部构建，再串行测量，没有构建/测试与测量重叠。

每候选包含 90 条无探针批量记录、90 条带探针批量记录，以及 240 条无探针完整流记录。完整流仍使用每流 250 次 write+flush、32/8192 注册流、200 次无关文件重命名，覆盖冷/热索引、增长/预留容量。合计 840 条记录，见 [原始 JSON 与可执行文件哈希](benchmarks/append-batch-scan-20261011.json)。基线与候选二进制哈希已确认不同。

## 候选一：单趟回收已完成任务

reap 从上次命中的位置继续查找并直接轮询那个完成句柄，避免从队首重新扫描未完成前缀。句柄仍在流中保留到取得结果；失败处理与中止语义不变。单请求不新增集合、通知或分配。

无探针结果，中位数吞吐 MiB/s / 各轮整批 p99 微秒，原版→候选：

- 批大小 1：3490.04 / 12.3 → 3435.88 / 12.4。五批各自的吞吐中位数相对变化：+12.35%, -4.95%, -3.15%, -2.84%, +19.08%。
- 批大小 16：3267.77 / 196.6 → 3596.26 / 202.3。五批各自的吞吐中位数相对变化：+3.86%, +13.18%, -1.49%, +10.83%, +2.13%。
- 批大小 64：2335.23 / 959.9 → 2372.99 / 968.1。五批各自的吞吐中位数相对变化：+2.25%, -0.03%, -3.74%, +1.92%, +38.42%。

诊断批大小 64：平均每请求句柄检查次数的逐轮中位数仅从 126.95 降到 126.76，扫描计时从 1239.20 降到 1198.57 ns/请求。基线 reap 调用约 2.0095 次/请求，其中每次写入固定检查两次，额外回收循环很少。这支持如下判断：该负载的大部分扫描发生在任务尚未完成时，优化连续完成积压并没有命中主要重复工作。

未看到稳定端到端收益，撤回该候选。

## 候选二：多任务时先轮询原有预算 future

仅当 pending.len() > 1 时，先轮询已经创建并固定的 semaphore acquisition future。若立即获得预算，省去此次 select 内的完成句柄扫描；若 Pending，继续使用同一个 future，保留预算队列位置，并恢复原有优先观察完成错误的 select。获取预算前后原来的 reap 均保留。不是 try_acquire，也没有绕过早到大请求的预算预留。

无探针结果：

- 批大小 1：3647.35 / 12.2 → 3600.61 / 12.3。五批各自的吞吐中位数相对变化：-12.87%, +4.47%, -2.28%, +5.34%, -5.86%。
- 批大小 16：3629.15 / 202.5 → 3535.42 / 178.2。五批各自的吞吐中位数相对变化：+2.55%, -5.48%, -3.59%, +4.90%, +6.25%。
- 批大小 64：2391.15 / 969.9 → 2403.14 / 995.0。五批各自的吞吐中位数相对变化：-4.26%, +20.59%, +0.17%, +4.61%, -5.48%。

诊断结果：批大小 16 的检查次数约 32.48→25.16 次/请求、扫描计时 556.33→399.80 ns/请求；批大小 64 约 126.99→96.22 次/请求、1228.10→738.01 ns/请求。单请求仍为 2 次句柄检查。

带探针时，批大小 16 吞吐 2854.15→3055.55 MiB/s，批大小 64 为 2109.19→2285.97 MiB/s，五批方向均为正；但不带探针时没有重现这个稳定趋势。因此只能确认扫描量下降，不能确认生产吞吐改善。计时器、聚合计数器和其它诊断会改变成本与调度；减少诊断调用也会放大带探针的收益。批大小 1 的无探针方向也在批次间变化，未证明不会影响单请求表现。候选撤回。

## 保留的回归

- 首请求被门闩阻塞，31 个后续请求完成；空写必须不阻塞，之后两次取消 flush 并追加一个请求，最终释放门闩，验证全部 33 个不同字节的位置和零在途字节。覆盖批量回收后仍保有未完成前缀的所有权。
- 小流有两个请求在途，较早的 8 字节大请求已经预留空闲预算，小流再申请 1 字节必须排队。释放前三个任务后，大请求仍先得到预算；小请求处理自身两个完成任务后，还必须先于后来排队的另一个 8 字节请求获得预算，验证 acquisition 队列位置没有丢失/重置。验证最终数据、峰值预算及零在途字节。

两个测试都使用确定性门闩和手动 poll，不用 sleep 猜测调度。第二个候选的完整诊断回归 303 项通过；恢复原实现后再次运行默认 Rust 301 项、诊断构建 303 项，各 13 ignored，全部通过。默认公平协调器、取消、失败传播和本地 HTTP 模拟回归均包含在内。Java/JNI 未改，本轮未重跑 JNI/Hadoop，也未进行真实云服务验证。

## 复现

按照项目构建脚本准备 Windows MSVC/SDK 环境，在项目目录执行：

```powershell
$env:OBS_APPEND_BENCH_REQUESTS='8192'
Remove-Item Env:OBS_APPEND_PROFILE -ErrorAction SilentlyContinue
cargo test --locked --release -p obs-rust-core --test filesystem append_latency::benchmark_append_completion_batches -- --exact --ignored --nocapture
$env:OBS_APPEND_PROFILE='1'
cargo test --locked --release -p obs-rust-core --features append-diagnostics --test filesystem append_latency::benchmark_append_completion_batches -- --exact --ignored --nocapture
```

工作区保留 `work/benchmark_batchscan.ps1`、`work/benchmark_batchscan_budget.ps1`、两个候选源码与独立二进制、原始日志；脚本交替顺序且拒绝覆盖既有日志。恢复生产文件时更新时间戳以强制 Cargo 重建，最终文件哈希与本轮原件一致。目标项目不包含被撤回候选。
