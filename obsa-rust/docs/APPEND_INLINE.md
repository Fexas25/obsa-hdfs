# 单流槽位索引与追加任务分段计时

2026-10-11。本轮保留冲突 FIFO、定向通知和惰性索引策略，减少构建/更新索引的
小数组分配，并补齐存储任务的派发、轮询、清理和返回阶段。核心仍为纯 Rust，
Hadoop/JNI API 和默认构建方式不变。完整流尾延迟仍有混合结果，未宣称全面提速。

## 生产改动与验证范围

原来每个索引路径都用 Vec<usize> 保存槽位。现在一个槽位直接存入 TargetSlots::One，
只有同一路径出现多个流时才使用 Many(Vec)。因此 8192 个不同路径首次建索引不再为
这些单元素槽位各分配一个 Vec；路径字符串和 HashMap 自身仍有分配，未测 RSS，
也没有据此宣称总内存下降了某个百分比。索引桶值的布局也发生变化。

注册、索引重建和文件 rename 后重建相关桶共用这套表示；源与目标桶仍先一起移除，
再更新与重新归类，防止把已移动的源作为旧目标误处理。无关路径不扫描，目录路径
继续使用原连续注册表。队列、阻塞者选择、许可释放与取消语义没有修改。

新增确定性回归：已有单流索引后注册第二个同名流，重命名必须等待它的活动追加；
一个流退出后再次移动、再注册同名流，所有存活路径仍正确更新。已有覆盖目标失效、
目录、索引压缩、公平性和取消测试全部保留。

## 索引构建与协调器对照

索引构建采用三个交替顺序批次，每种条件共 30 次记录，计时仅包含锁内构建；
每次运行先预热一次。以下为中位数与 min–max，范围不是置信区间。

- 32 流 / 不同路径：0.005（0.005–0.012） → 0.004（0.004–0.007） ms。

- 32 流 / 同名：0.003（0.002–0.004） → 0.003（0.003–0.003） ms。

- 8192 流 / 不同路径：2.625（1.958–6.963） → 2.188（1.548–5.534） ms。

- 8192 流 / 同名：0.626（0.513–1.353） → 0.586（0.495–1.108） ms。

8192 个不同路径的构建中位数 2.625 → 2.188 ms，约减少 17%。这是本轮最直接的
锁内成本收益；不要与上一轮不同时间测得的 1.681 ms 拼接成趋势。

协调器合成基准用 64 个任务，分别按 before→after、after→before 两种顺序运行，
每个场景每版六轮。这里只是协调器合成工作，不是 HTTP、JNI 或实际追加吞吐。

- 32 流、32 文件：1813474.484（1439706.660–2020444.371） → 1912646.594（1158551.376–2610231.291） ops/s；追加 p99 0.187（0.123–0.340） → 0.128（0.102–0.318） ms。

- 1024 流、1024 文件：1762341.235（1091034.932–2202499.148） → 1987356.925（1634020.303–2250921.471） ops/s；追加 p99 0.205（0.114–0.666） → 0.137（0.094–0.164） ms。

- 8192 流、8192 文件：1370649.722（852485.395–2372338.533） → 1834624.179（1322248.484–2058308.006） ops/s；追加 p99 0.277（0.088–0.626） → 0.136（0.096–0.240） ms。

- 8192 流、1 文件：105592.631（87211.948–122975.681） → 110559.604（93302.961–190955.512） ops/s；追加 p99 4.415（3.293–6.504） → 4.210（2.408–5.383） ms。

- 8192 流、8192 文件、目录 rename：73198.377（63099.071–90145.848） → 81486.133（68649.537–152368.654） ops/s；追加 p99 6.183（4.431–9.186） → 5.249（2.872–6.563） ms。

- 1024 流、1024 文件、模拟 1 ms sleep：4076.471（4003.066–4084.826） → 4081.550（4071.575–4103.573） ops/s；追加 p99 16.623（16.505–17.093） → 16.474（16.277–16.648） ms。

首轮连未改动的目录逻辑也出现明显加速，所以补了反序运行。合并后目录仍有变化，
说明环境、编译布局或运行时序会影响结果；不能把每个场景的全部增幅都归为此优化。
Windows 上模拟 1 ms sleep 的实际尾延迟约 16 ms，不应解释为客户端固定延迟。

## 最终完整流对照

先后进行了两轮完整流实验。首次记录保留在机器数据的 initial 分组及
work/append-inline-first-pass-*.log。诊断代码全部完成后重建最终默认二进制，
再运行 final 对照，避免把先前构建当作最终产物。两轮结果都保留，不混合统计。

每轮实验三批交替顺序，每个条件每版九个记录轮次；每个进程先预热一轮。
四个写入任务各执行 250 次 4 KiB write+flush，另有 200 次无关文件 rename；
32 或 8192 表示注册流数。所有轮次验证最终长度和全部字节。下面列出 final：

- 32 流 / copy / cold：吞吐 16.927（14.400–20.397） → 16.937（13.571–21.304） MiB/s；追加 p99 4.656（3.258–8.810） → 5.210（3.528–7.963） ms。

- 32 流 / copy / warm：吞吐 16.248（12.399–20.181） → 16.550（13.971–22.904） MiB/s；追加 p99 6.651（3.888–8.339） → 5.834（3.219–8.074） ms。

- 32 流 / inplace / cold：吞吐 524.526（499.323–599.596） → 562.941（475.583–585.610） MiB/s；追加 p99 0.198（0.175–0.238） → 0.191（0.172–0.308） ms。

- 32 流 / inplace / warm：吞吐 553.536（507.371–602.240） → 571.950（469.140–589.640） MiB/s；追加 p99 0.196（0.144–0.225） → 0.196（0.177–0.254） ms。

- 8192 流 / copy / cold：吞吐 19.238（16.056–21.259） → 18.985（15.607–19.636） MiB/s；追加 p99 4.517（3.061–7.778） → 4.156（3.605–6.822） ms。

- 8192 流 / copy / warm：吞吐 18.466（11.371–20.381） → 19.015（15.905–20.636） MiB/s；追加 p99 6.861（3.341–11.317） → 4.643（3.068–7.338） ms。

- 8192 流 / inplace / cold：吞吐 187.404（181.677–194.667） → 189.827（166.553–198.195） MiB/s；追加 p99 0.270（0.221–0.360） → 0.268（0.192–0.349） ms。

- 8192 流 / inplace / warm：吞吐 210.400（178.139–216.306） → 199.256（176.338–214.025） MiB/s；追加 p99 0.213（0.192–0.408） → 0.223（0.216–0.307） ms。

8192 流默认复制模式的冷启动追加 p99 为 4.517 → 4.156 ms，但吞吐略降；容量复用
预热条件的吞吐与 p99 都退步。首次实验中容量复用冷启动 p99 也曾退步。因此保留的
结论是减少了索引构建的分配与持锁成本，而非完整流在所有条件下都更快。

## 可选任务诊断

新增 Cargo feature `append-diagnostics`，默认不启用。默认构建没有诊断字段、
观察器或计时调用；Hadoop/JNI 默认构建不启用它。通过
PfsAppendStream::with_task_diagnostics 关联独立、有记录条数上限的采集器。
超出上限只增加 dropped 计数，不再保留记录；基准每个流限制 250 条并检查没有丢弃。
诊断采集器自身有开销，其内存不计入生产数据缓冲预算；用于受控本地分析。

新增任务记录按单调时钟分为五段，其和逐次等于 write+flush 总耗时：

- prepare：写入开始至调用 spawn 前，包含预算、协调准入和缓冲准备。
- dispatch：spawn 前至任务首次执行，包含 spawn 开销及任务被调度的等待。
- service：任务开始至存储请求返回并释放请求 Future，包含存储观察器开销。
- cleanup：至任务观察器析构，包含字节/命名空间许可释放及缓存和用户回调。
- join：至写入方 flush 返回，包含诊断记录发布、任务完成、写入方调度与 flush 回调。

另外记录存储 Future 的 poll 次数及首次唤醒到下次 poll 的累计延迟；后者与 service
重叠，不能再加进五段总和。保留上一轮的写入 Future 唤醒计时、对象锁等待和持锁
计时，从而可以同时观察外层任务与内部存储锁。上述标记并非 OS 线程调度追踪。

观察器使用 RAII：成功和错误返回均记录 store_finished；任务取消也保留记录。
若未首次执行就被取消，started 为 None，此时不应用正常清理阶段的解释。
store_finished 为 None 也可能表示未返回即取消或展开，并不代表服务端一定未提交。
测试覆盖记录上限、首次执行前释放，以及实际任务的成功、失败、挂起后取消，
并检查任务回调期间记录尚未发布、之后记录才可见，不改变原错误传播与清理顺序。

## 新诊断证据

共取得 24,000 次双层记录，并逐次验证两套五段计时都严格相加等于同一个总耗时。
在 8192 流默认复制冷启动中，三轮各最慢十次追加合计的 prepare/dispatch/service/
cleanup/join 占比分别约 0.02% / 9.13% / 90.76% / 0.02% / 0.07%。
预热后的 service 占比约 96.31%。这是该组尾部操作累计延迟占比，不是 CPU 占比。

容量复用的冷启动尾部 prepare 占比约 61.45%，预热后约 0.21%；首次索引构建对
启动阶段的影响仍然存在，即使已经减少分配。不能将所有 prepare 都称为锁等待。
默认复制场景的主要慢段仍在存储内，继续削弱公平队列没有证据支持。

全部 24,000 个模拟存储请求都是一次 poll 即完成，存储 Future 唤醒延迟为零。
这说明模拟实现没有异步等待网络，但其同步对象 Mutex 会阻塞线程，OS 抢占与锁等待
仍包含在 service 中；零异步唤醒不是“没有调度影响”。带观察器结果含额外开销，
不能与无观察器的吞吐、p99 直接做绝对比较。真实云端需另行验证。

## 复现与验证

默认性能入口仍为 scripts/build-windows.ps1 -BenchmarkAppend。观察存储任务需要
在配置好 MSVC/Windows SDK 的 PowerShell 中执行：

```powershell
$env:OBS_APPEND_PROFILE = '1'
cargo test --locked --release -p obs-rust-core --features append-diagnostics --test filesystem benchmark_append_filesystem -- --ignored --nocapture
Remove-Item Env:OBS_APPEND_PROFILE
```

也可以先在同一 PowerShell 中执行 scripts/build-windows.ps1 -SkipTests 配置工具链。
OBS_APPEND_BENCH_PREWARM、OBS_APPEND_BENCH_INPLACE 分别控制预热与容量复用；它们
按是否存在判断，关闭必须移除变量。性能跑次需与编译和其他负载隔离。

默认 Rust 293 通过；诊断 feature 构建 295 通过，两者各 11 ignored（性能基准）。
首次网络受限的 HTTP 测试运行已中止并保留日志，允许本地网络后同一源码全部通过。
JNI 冒烟通过；Hadoop 291 项中 279 通过、12 按原配置跳过，零失败/错误。

原始对照、范围和版本/日志 SHA256 见
[机器可读结果](benchmarks/append-inline-20261011.json)。完整诊断轨迹位于工作区
outputs/append-inline-task-traces.jsonl.gz。工作区 benchmark_append_inline.ps1、
benchmark_append_inline_index.ps1、summarize_append_inline.py 保留运行及校验步骤。
日志前缀 work/append-inline-，包括默认/feature/JNI/Hadoop 回归。

后续边界：首次建索引仍同步持锁；目录/文件交替导致索引重建的压力尚未完整量化；
默认模拟存储的全局对象锁与整文件复制仍主导尾部。没有真实桶、跨实例或云吞吐结论。
