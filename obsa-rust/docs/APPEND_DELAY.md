# 追加并发：异步延迟与预算对照

2026-10-11。本轮补齐异步服务等待的模拟和取消回归，未修改生产代码、默认并发或预算。结果表明，上一轮低延迟内存后端的最优并发不能直接套用于有等待的服务。

## 模型与实验

range-object 后端在 append 提交数据前执行可取消的 Tokio sleep。等待不持有对象表锁、对象锁或旧模式的全局串行锁；等待结束后按原逻辑提交定位写入。这仅模拟异步提交前的等待，不模拟 HTTP、网络带宽、连接池、服务端限流或真实 OBS/PFS。

新增 `OBS_APPEND_BENCH_DELAY_MS`，默认 0、范围 0..=1000。每条结果同时输出配置延迟及 delay_stats：进入等待的 calls、仍等待的 active、峰值 peak、等待累计 elapsed_ns。取消也计入 calls/elapsed，但不提交数据。active/peak 只覆盖延迟阶段，不等于所有生命周期状态下的任务数。elapsed_ns 是各请求等待的累加，会随并发重叠，不能除以墙钟时间当作 CPU 占比。

实验使用 4 写入流、Tokio 4 工作线程、4096 字节请求、每流 64 请求、预留最终对象容量，每场景每轮 1 MiB。比较延迟 0/2 ms、并发 4/64、共享预算 64 MiB/16 KiB、批大小 1/16/64。五批轮换配置顺序，每进程一轮预热＋三轮记录，每条件 15 条，共 360 条。先完成构建和回归，再串行测量。未启用 append-diagnostics 任务分段探针，但延迟模式包含上述计数和计时开销。

短负载用于判断配置与异步等待的关系。批大小 16 每轮只有 16 个批次样本，批大小 64 只有 4 个，二者的 p99 实际都是该轮最大值，不能据此声称尾延迟稳定改善。零延迟短测量也不替代上一轮 128 MiB 长测量。原始结果见 [JSON 与二进制 SHA256](benchmarks/append-delay-20261011.json)。

## 结果

下列数值为逐轮中位数吞吐 MiB/s，并发 4→64。括号依次给出峰值等待请求数，以及每轮请求平均实际等待时长的中位数（毫秒）。

### 配置延迟 0 ms，预算 64 MiB

- 批大小 1：2140.41（0；0.000 ms） → 1976.28（0；0.000 ms）。
- 批大小 16：2298.85（0；0.000 ms） → 1391.21（0；0.000 ms）。
- 批大小 64：2172.97（0；0.000 ms） → 990.59（0；0.000 ms）。
### 配置延迟 0 ms，预算 16 KiB

- 批大小 1：2418.96（0；0.000 ms） → 1897.53（0；0.000 ms）。
- 批大小 16：2139.50（0；0.000 ms） → 1644.20（0；0.000 ms）。
- 批大小 64：2194.91（0；0.000 ms） → 2104.82（0；0.000 ms）。
### 配置延迟 2 ms，预算 64 MiB

- 批大小 1：1.01（4；15.491 ms） → 1.01（4；15.445 ms）。
- 批大小 16：4.04（16；15.398 ms） → 16.59（64；14.725 ms）。
- 批大小 64：4.04（16；15.451 ms） → 62.41（256；13.922 ms）。
### 配置延迟 2 ms，预算 16 KiB

- 批大小 1：1.01（4；15.472 ms） → 1.01（4；15.487 ms）。
- 批大小 16：1.01（4；15.455 ms） → 1.00（4；15.492 ms）。
- 批大小 64：1.01（4；15.447 ms） → 1.01（4；15.451 ms）。

配置 2 ms 时，实际平均等待约 14–15.5 ms，包含本机定时器唤醒与调度开销，不能把这次实验当作精确 2 ms 服务 RTT 测试。未修改系统定时器精度或电源设置。

宽预算下，批大小 64 时并发 64 的峰值等待数达到 256，并发 4 为 16，更多请求可重叠服务等待，因此吞吐方向与零延迟场景相反。16 KiB 预算仅够四个请求，两种并发上限的峰值都为 4，吞吐均约 1 MiB/s；提高每流并发无法突破共享预算限制。批大小 1 的峰值也是 4，上限 4/64 都不会被用满。

这些数字没有用于修改默认值。生产仍默认每流并发 4、共享追加请求体预算 64 MiB。真实环境需要同时测服务延迟、请求大小、流数量、连接池和预算；既不能凭内存后端结果全面压低并发，也不能凭本次延迟模拟全面提高并发。

## 验证与保留内容

新增虚拟时间确定性测试，覆盖对象锁模式与旧全局串行模式：两个 append 均进入等待、其它对象 put/list/snapshot 可继续；推进至延迟未满时仍不完成；取消一个请求，等待计数下降且没有数据写入；另一个请求在推进时间后写入成功，最终 active 为零。没有使用真实 sleep 猜测测试时序。

所有基准均验证最终数据、零在途等待、延迟调用数；汇总时另校验峰值不超过 min(四个流的并发总上限, 预算/4096)。默认 release filesystem 151 项、诊断构建 152 项通过，各 4 ignored。生产公平性和取消实现没有改动；本轮未重跑无关 HTTP/JNI/Hadoop 测试，也没有真实云验证。

保留新增模拟延迟、可取消的等待计数、回归测试及基准参数。README 补上现有 fs.obs.pfs.append.concurrency 配置说明，明确它与共享字节预算共同约束实际并发。

## 复现

按项目 Windows 构建脚本准备 MSVC/SDK 环境，在项目目录执行：

```powershell
$env:OBS_APPEND_BENCH_REQUESTS='64'
$env:OBS_APPEND_BENCH_DELAY_MS='2'
$env:OBS_APPEND_BENCH_CONCURRENCY='4' # 改为 64 对照
$env:OBS_APPEND_BENCH_TOTAL_BYTES='67108864' # 改为 16384 对照
Remove-Item Env:OBS_APPEND_PROFILE -ErrorAction SilentlyContinue
cargo test --locked --release -p obs-rust-core --test filesystem append_latency::benchmark_append_completion_batches -- --exact --ignored --nocapture
```

五批脚本 work/benchmark_append_delay.ps1、原日志、可执行文件保存在授权工作区。脚本拒绝覆盖旧日志。需要可靠尾延迟或性能发布结论时，应增加批次样本和负载持续时间，并加入真实测试服务验证；当前数据只说明模拟条件下的配置关系。
