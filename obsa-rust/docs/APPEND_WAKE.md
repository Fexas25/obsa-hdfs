# 公平队列的定向通知与性能复测

本页保留定向通知阶段的数据；后续完整流瓶颈定位与路径索引优化见
[APPEND_FLOW.md](APPEND_FLOW.md)。

2026-10-11。保留前序冲突优先、后来的 rename 不能越过已等待追加的准入规则，
减少无关完成引起的唤醒、重复目标表扫描和追加完成时的锁竞争。核心仍为 Rust；
本轮没有新增 Java 算法或更改 Hadoop 能力声明。


同环境顺序对照的最终版在 64 任务同文件/目录热点上，吞吐中位数分别为原版的约
2.47/2.36 倍，追加 p99 从 4.992/8.527 ms 降至 2.136/2.683 ms。四任务热点也有改善，
但四任务目录的 max 中位数从 8.890 ms 升至 18.719 ms。完整流交替测试的 8,192 流
吞吐中位数从 16.40 降至 15.54 MiB/s，追加 p99 从 6.459 升至 7.326 ms，区间重叠明显。
这支持热点协调路径改善，不能证明端到端全面加速；退步及全部异常值均保留。

## 实现

- 追加/注册等待具体的前序 rename；rename 等待具体的前序冲突项或相关流排空。
  完成状态是持久标记，先注册通知再检查状态，避免完成早于等待时丢失唤醒。
- 存在前序队列冲突时，跳过整个流目标注册表扫描。仍由原有冲突队列判定准入顺序，
  无关路径可推进，流等待项随成功 rename 更新目标身份对应的路径。
- 排队追加成功准入后，通知责任转移到在途许可，直到请求结束才唤醒依赖它的 rename。
  取消等待、失效错误和成功注册仍及时清理队列并通知。
- 追加许可退出只锁流目标，不再锁协调器；只有最后一个请求结束且存在排空订阅时
  才调用 Notify。订阅正常完成或取消均以 RAII 归还，避免无等待者时也进入 Notify 的内部锁。

没有更改远端请求、路径替换保护和不确定 rename 的流失效策略；状态锁不跨网络等待。
事件和队列属于额外元数据，未计入有效载荷预算，未测量此次改动的进程 RSS。

## 正确性验证

新增六项确定性回归：无关追加完成不唤醒受阻追加；无关流排空不唤醒 rename；
排队追加准入不提前通知而取消/完成会通知；同流最后一个许可才通知；完成早于订阅
不丢失通知；取消排空等待释放订阅。使用计数 Waker/手动 poll，无睡眠阈值断言。
前两项在旧实现稳定失败（work/append-wake-before.log），修复后与原公平排队测试全通过。

最终源码：Rust 284 通过、10 个性能用例默认 ignored；JNI 冒烟通过；Hadoop 291 项，
279 通过、12 按原能力跳过、零失败/错误。原始日志为 work/append-wake-{rust,jni,hadoop}.log。

## 测量方法与保留证据

沿用未修改的两份 release 基准：一轮预热、三轮测量、轮转场景、四个 Tokio 工作线程，
协调器分别使用 4/64 个追加任务；每任务 1,000 次追加，共 200 次 rename。计时包含
人工 yield 或 sleep 和协调等待。吞吐分母是整批总耗时，不能解释为 HTTP 数据吞吐。
完整 MemoryStore 文件系统始终只有四个写任务，4 KiB write+flush，各 250 次。

保留全部版本/运行：before 是上轮历史公平队列；wake/repeat 是初版定向通知及复跑；
control 是当前环境重跑原公平实现；final 是加入排空订阅计数的最终实现。
主基准按块顺序运行，不是随机交替配对 A/B；不能排除机器负载和调度漂移。
发现完整流结果不稳定后，额外交替执行原版和优化版文件系统可执行文件，三批、每批
各有预热与三次计时，批次交替先后顺序。初版和最终版的交替结果均保留。
源码、可执行文件和基准散列以及全部原始试验见
[append-wake-20261011.json](benchmarks/append-wake-20261011.json)。
以下 p99 和 max 是三次试验各自统计量的中位数，不是合并样本百分位。

## 延迟模拟与最大停顿

配置 1 ms sleep 的场景在本 Windows 环境往往表现为约 16–17 ms，不能作为真实网络 RTT。
初版四任务曾出现 342.221 ms 的单次追加最大值，即使其 p99 仍约 16.56 ms；该异常没有
删除。公平排队保证的是已登记冲突请求的次序，不是固定毫秒截止时间，也不能约束 OS
调度、定时器或调用者不释放许可造成的等待。

- 4 任务延迟模拟：吞吐 257 → 257；追加 p99 16.595 → 16.559 ms；最终版三轮 max 范围 24.41–29.25 ms。

- 64 任务延迟模拟：吞吐 4078 → 4067；追加 p99 16.624 → 16.600 ms；最终版三轮 max 范围 32.18–333.99 ms。

以下每个版本/流规模各九个计时试验，仍统计试验级中位数及范围，吞吐为有效载荷 MiB/s。

- 8192 流，原版：吞吐 16.40（13.35–18.54）；追加 p99 6.459 ms（4.607–8.199）；rename p99 3.632 ms（0.677–13.414）。

- 8192 流，最终版：吞吐 15.54（13.90–17.86）；追加 p99 7.326 ms（4.482–8.253）；rename p99 5.455 ms（2.589–8.930）。

该模拟存储每次追加在全局对象锁内复制整个增长中的文件，还记录调用并更新缓存。
它不能用来代表 HTTP/JNI/真实 PFS 数据面，更不能仅凭协调器的提升声称端到端同幅加速。
初次顺序运行的完整流大幅下降在交替初版测试中未稳定复现；全部原始结果仍保留。

## 尚存限制

协调器准入仍有短时共享互斥锁；冲突队列查找/移除和获准 rename 的注册表扫描仍是线性的。
大目录成功移动仍须更新关联流路径。高并发的调度和互斥竞争、MemoryStore 复制/缓存开销
尚未通过 CPU profile 分离。本轮没有真实桶、Linux、多实例协同或跨进程公平性验证，
也没有证明所有负载下都更快或给出绝对等待上限。
