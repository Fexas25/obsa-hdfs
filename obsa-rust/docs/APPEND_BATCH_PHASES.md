# 批量追加：任务排队与默认并发对照

2026-10-11。本轮只完善基准与诊断，不修改生产实现或配置默认值。发现此前固定并发 64 的批量压力场景不能代表生产默认并发 4；保留两者可切换的对照，并补上提交、任务阶段和 flush 分段。

## 方法与指标边界

range-object 隔离内存后端、Tokio 4 工作线程、4 写入流，每流 8192 个 4096 字节请求，单场景每轮 128 MiB，批大小 1/16/64，预留对象最终容量，无并发 rename。每个实验五批交替配置和探针模式顺序，每进程一轮预热＋三轮记录，每条件 15 条记录。构建和回归均在计时运行前完成，测量串行执行。

两个独立实验各 180 条记录：预算实验固定并发 64，比较配置预算 64 MiB/16 KiB；并发实验固定预算 64 MiB，比较每流并发 4/64。合计 360 条聚合记录，见 [数据与二进制 SHA256](benchmarks/append-batch-phases-20261011.json)。两轮实验的基线不合并。预算实验当时的源码固定并发 64，存档中为这些记录补充明确的 concurrency=64 字段；后续构建直接输出 concurrency 字段。

无探针结果用于吞吐和尾延迟比较。带探针结果使用已有的有界任务时间戳，额外记录每批写入开始、全部 write 返回、flush 返回三个时刻，并在计时结束后汇总：

- write：开始提交批次至全部 write 返回，包括缓冲区分配、协调、预算和并发等待、调度；不能单独解释为预算等待。
- flush_overlap：write 返回至最后一个任务被观察为完成，若所有任务已完成则为零。
- flush_tail：max(write 返回、最后任务完成记录) 至 flush 返回；包含诊断记录写入、运行时结束/唤醒/调度和 flush 尾部处理，不是纯通知 CPU 时间。
- dispatch：任务记录建立至任务开始执行；包含 spawn 成本和调度等待。
- service：任务开始至存储 future 返回；包含模拟存储、其对象锁和探针成本。
- cleanup：存储返回至任务完成记录；包含资源归还、回调和可能的调度中断。

每个任务的位置、起止顺序、所属批次边界均校验；flush_overlap + flush_tail 的累计值必须等于 flush 总耗时。最终验证每个对象的长度和全部内容，诊断记录无丢弃。样本数组按批次数预留容量，减少采样数组增长带来的干扰。基准总吞吐计时仍包含 barrier、close、任务回收和样本合并等驱动成本，不等同于纯存储吞吐。

各阶段之间存在并行重叠；任务分位数不能相加，跨流累计耗时也不是 CPU 使用率。探针会改变调度和分配，不能把有探针的分段比例套用到无探针吞吐。

## 预算实验

无探针中位数吞吐 MiB/s / 每轮整批 p99 微秒，64 MiB→16 KiB：

- 批大小 1：3849.61 / 11.3 → 3801.30 / 11.7。
- 批大小 16：3825.19 / 155.3 → 3272.85 / 194.0。
- 批大小 64：2665.28 / 810.9 → 3350.36 / 596.9。

带探针的批大小 64，宽预算下累计 write/flush_overlap/flush_tail 占比约 38.93%/60.66%/0.40%，dispatch p99 的逐轮中位数 627.1 μs；紧预算后分别约 98.42%/0.99%/0.59%，dispatch p99 约 3.2 μs。限制在途请求后，等待主要移到提交阶段，任务队列缩短；不能把这种等待位置变化都当成减少了工作。

16 KiB 预算至多容纳四个 4096 字节请求，而四个流各并发 64 最多可有 256 个请求。宽预算在这个负载中不约束在途数据，紧预算因此是明显的反压实验。紧预算在批大小 16 的吞吐反而下降，不能据单个条件调低生产预算。

## 并发实验

生产 ObsConfig 的默认并发为 4、默认追加字节预算为 64 MiB；此前批量基准显式设为并发 64。现在可设置 OBS_APPEND_BENCH_CONCURRENCY，输出也明确标注配置。

以下为同一并发实验内的无探针结果，中位数吞吐 MiB/s / 整批 p99 微秒，并发 64→4：

- 批大小 1：3437.17 / 12.5 → 3646.30 / 11.6。五批吞吐变化：+10.54%, +11.47%, +4.93%, -0.14%, -2.79%。
- 批大小 16：3375.40 / 202.5 → 3774.29 / 168.4。五批吞吐变化：+13.66%, +28.39%, +19.45%, +2.57%, -5.30%。
- 批大小 64：2249.56 / 967.0 → 3664.79 / 537.9。五批吞吐变化：+78.75%, +83.82%, +80.09%, +62.71%, +44.50%。

批大小 64 的吞吐方向在五批中一致。带探针的 dispatch p99 从 704.0 降至 55.5 μs，累计 write 占比从 38.95% 升至 96.30%，flush_tail 仅约 0.51%→0.25%。这些证据支持：此高并发本地负载的重要成本在任务执行前的排队，最终任务完成后的 flush 尾部占比较小。完成轮询和通知也可能发生在 write 或 flush_overlap 内，因此较小的最终尾部不能排除整个完成机制的成本。仍未用 CPU 采样区分运行时内部和模拟对象锁的细项。

批大小 1 每次写后立即 flush，实际不会达到并发 4 或 64 的上限，所以该条件的配置间吞吐差异主要用作运行噪声参照，不能宣称改变上限提升了单请求性能。

这是低延迟内存后端的结果。真实 OBS/PFS 的网络 RTT、服务端并发和连接池会改变最优在途数，不能把这些数值作为云吞吐预测。生产默认并发已经是 4，本轮保持现状，不引入自适应调参或默认值变更。

## 验证与复现

最终 release filesystem 回归：默认构建 150 项、诊断构建 151 项通过，各 4 ignored；两个实验的手动基准全部通过数据、时序和聚合断言。本轮没有修改 src 下的生产文件、Java/JNI 或取消/公平队列；没有重跑无关 HTTP/JNI/Hadoop 回归，也没有真实云服务验证。

先按项目脚本准备 Windows MSVC/SDK 环境，在项目目录运行：

```powershell
$env:OBS_APPEND_BENCH_REQUESTS='8192'
$env:OBS_APPEND_BENCH_CONCURRENCY='4' # 设置 64 对照压力场景
$env:OBS_APPEND_BENCH_TOTAL_BYTES='67108864' # 设置 16384 对照紧预算
Remove-Item Env:OBS_APPEND_PROFILE -ErrorAction SilentlyContinue
cargo test --locked --release -p obs-rust-core --test filesystem append_latency::benchmark_append_completion_batches -- --exact --ignored --nocapture
$env:OBS_APPEND_PROFILE='1'
cargo test --locked --release -p obs-rust-core --features append-diagnostics --test filesystem append_latency::benchmark_append_completion_batches -- --exact --ignored --nocapture
```

请求数范围 64..=16384 且为 64 的倍数；并发范围 1..=256。基准请求单位固定 4096 字节，预算必须至少 4096；输出预算是配置值，超大配置仍遵循生产预算构造时的上限限制。为维持历史压力基准可比性，未设置并发变量时基准仍为 64，与产品默认值的区别已明确记录。

授权工作区保留 work/benchmark_batchphases.ps1、work/benchmark_batchphases_concurrency.ps1、原始日志和两个阶段的二进制；脚本五批交替顺序且拒绝覆盖旧日志。相同总请求数下，不要跨不同批大小直接比较整批 p99。
